# CLAUDE.md

## Project rules (multi-week build — see PLAN.md / PROMPTS.md)

Every session working on the Agent Workspace Simulation build follows these:

- UI components never import the simulation bus, TTS/ASR, the store, or any vendor SDK directly; they consume the provider interfaces via the provider context only.
- Vendor payloads (Twilio, CXone, anything) never reach components; adapters map them to the app-owned domain model at the edge.
- Every provider method is async; all state changes arrive as events, even in the simulation. Simulation injects configurable latency.
- Panels, cards, pickers, and AI handlers render from the active ContactCenterProfile's schema/terminology — never hard-coded entity fields.
- The AI never writes to the database silently; drafts fill live, the agent confirms.
- The customer console is sim-only; the agent UI must not know it exists.
- Verification scales to risk: type-check always; tests when they exist; browser click-through only when a step's done-criteria require it. Git is the backup — no manual .bak copies.
- Keep steps narrow: in large page files, grep and make targeted edits rather than reading whole files.
- Before starting any step, read PLAN.md and PROGRESS.md.
- Don't add Co-Authored-By, Claude-Session or any other attribution lines to commit messages.

## lyra-ui usage

This app consumes the shared `lyra-ui` design system via a live source alias (`@nicecxone/lyra-ui`), not a local component library. Before writing or editing any UI code here:

## Rule zero: never hand-roll a button

**Every clickable, button-shaped element in this app is `Button`, `ActionIconButton`, or an existing lyra-ui button atom (`FavoriteButton`, `PanelPinButton`, `KebabMenuButton`, `OutboundAddButton`, etc.), imported from `@nicecxone/lyra-ui` — never a local hand-rolled `<button>` with copied or guessed styling, no matter how small the target looks (a single icon button, a pill, a toggle).** See `../lyra-ui/CONTRIBUTING.md`'s §0 for the incident this rule was written after: `lyra-ui`'s own `CreateNew` "New Outbound" trigger hand-copied `Button`'s colors correctly but used the wrong typography class for its label (`lyra-body-md`, 400 weight, instead of `lyra-label`, 500 weight) — two nearly-identical class names that only differ in weight, so the mismatch shipped and rendered visibly lighter than every other button until caught from a screenshot. Check this before writing or editing any button-shaped element here, every time.

- Import UI atoms from `@nicecxone/lyra-ui` — never build or reach for a local `src/components/ui/*` reimplementation of something that already exists there.
- Check `lyra-ui/src/index.ts` and that component's `__stories__` file *before* building anything — reuse the existing component, and match the exact markup shape shown in its story, not just the prop types (e.g. a plain labeled `Checkbox` is a manual `<label>` wrapper around it in most stories, not the `label` prop).
- Never modify a `lyra-ui` core component from here. If something this app needs doesn't exist yet in `lyra-ui`, that's a signal to add it there — not approximate it locally.
- When a screenshot or prompt describes a component ambiguously, or nothing in `lyra-ui` visually matches what's shown, ask the user which component to use or whether to build something new — don't guess. If building something new, keep it local to this app; don't add it to `lyra-ui` until the user explicitly asks (see `PROJECT_SUMMARY.md`'s "When a screenshot/prompt doesn't clearly match an existing component").
- Every modal's outer card uses `Container variant="modal"`, never a hand-rolled div.
- Use the shared `assets/app-icon.svg` mark for the app logo/smiley — never `CXoneSmiley` or a one-off hand-rolled SVG.
- Before reaching for a raw Tailwind utility value (spacing, sizing, radius, etc.), check other lyra-ui components/stories first for the established token.
- **Any `Popover` whose `content` is a `Menu`/listbox needs `bodyPadding={false}`.** `Popover`'s default `bodyPadding` adds its own 20px inset, which stacks on top of `Menu`'s own `p-1` row padding — the result renders, but reads as an over-padded, shrunken list (caught from a screenshot on the Interactions tab's bulk-actions "Change Status"/"Assign to Others" pickers, both `<Menu items={...} bare />` inside a `Popover`). See `../lyra-ui/CLAUDE.md`'s "Panels, menus & overlays" section for the general rule.

Full rationale, worked examples, and the "why" behind each of these live in `../lyra-ui/PROJECT_SUMMARY.md` (see Important Patterns, Scope Rules, and the Post-layout QA checklist) — read that file before making non-trivial UI changes here.

## File organization — new self-contained features get their own file

`AgentNextGenPage.tsx` grew to 779KB/14,380 lines before being split (Aug 2026) into `agent-next-gen-shared-utils.ts` plus one file per major feature area (transcript, outbound data, interaction dashboard, contact history, customers table, customer info panel) once it crossed Babel's 500KB code-generator threshold. Don't let it happen again: when adding a new, reasonably self-contained table/panel/card (e.g. an Accounts table, a Tickets table), build it in its own `src/components/*.tsx` file from the start and import it into `AgentNextGenPage.tsx` rather than adding another few hundred lines inline. Shared helpers (formatting, id/phone synthesis, etc.) belong in `agent-next-gen-shared-utils.ts` so new files can import from there instead of duplicating logic. Only keep something inline in the main file if it's small or is genuinely coupled to that component's own internal state/closures (in which case a clean split would require lifting state into context or heavy prop-drilling — flag that tradeoff rather than forcing it).

## Sync check (do this first, every session)

This app depends on a live sibling checkout of `lyra-ui` (see the `@nicecxone/lyra-ui` alias path in `vite.config.ts` — currently `../lyra-ui`), not a versioned package. `.lyra-ui-sync` in this repo's root records the `lyra-ui` commit hash this app was last checked against.

1. Confirm the sibling path from `vite.config.ts`'s alias and check it's a real git repo (`git -C ../lyra-ui rev-parse HEAD`). If it's missing entirely (this project was moved without lyra-ui alongside it, or lyra-ui hasn't been cloned yet), skip this check silently — don't block on it.
2. Otherwise, diff since last sync: `git -C ../lyra-ui log --oneline "$(cat .lyra-ui-sync)"..HEAD`. Nothing printed means nothing changed — move on.
3. If there are new commits, read `../lyra-ui/PROJECT_SUMMARY.md` for a human-readable description of what those changes actually are (its "Key Components" entries and changelog-style bullets exist for exactly this). Summarize for the user what's new and whether anything in this app looks like it should be migrated to use it (same categories as the rules above — a hand-rolled pattern that a new/changed component now replaces).
4. Ask before migrating anything — don't silently rewrite pages.
5. Whether or not the user chooses to migrate, once they've seen and responded to the new changes, update `.lyra-ui-sync` to `lyra-ui`'s current HEAD hash (`git -C ../lyra-ui rev-parse HEAD`) so the same commits aren't re-flagged next session.

`lyra-ux-templates` (a sibling mounted folder) uses this identical sync-check convention — if you're ever asked to set this up for a brand-new project duplicated from either template repo, copy `.lyra-ui-sync` and this `CLAUDE.md` over so the new project inherits the check automatically. Also make sure the new project's `tailwind.config.js` pulls its `theme.extend.colors` from `require("../lyra-ui/tailwind-tokens.cjs")` (spread into `colors: { ...lyraColors, /* any of this app's own one-off literals */ }`) rather than hand-copying the color list — see `../lyra-ui/tailwind-tokens.cjs`'s doc comment and `../lyra-ui/PROJECT_SUMMARY.md`'s "Cross-Repo Sync" section for the silent-failure bug this prevents (an unconfigured `bg-lyra-*`/`text-lyra-*`/`border-lyra-*` class generates zero CSS with no error).

## GitHub Pages setup (do this for every brand-new project, before the first deploy)

This app is a Vite SPA served from a GitHub Pages *project* page (a subpath like `https://<user>.github.io/<repo-name>/`, not the domain root). Left unconfigured, the site 404s or loads a blank page even when "Deploy from a branch" is turned on, because that setting only serves whatever's already built and pushed — it does not run a build step itself. For a new repo duplicated from either template, do all of the following, not just some:

1. Set `base: "/<repo-name>/"` in `vite.config.ts`, where `<repo-name>` is the *actual* GitHub repo slug for this project — not copied from whatever an earlier template/app used.
2. Fix `package.json`'s top-level `"name"` field to match this project too. It's easy to leave it as a copy-paste leftover from the template (this exact bug shipped in this repo — `"name": "lyra-ux-templates"` sat unnoticed in `agent-next-gen-v1/package.json` for a while); a wrong `name` is a signal something else was copy-pasted without review.
3. Add `gh-pages` and a `deploy` script: `"deploy": "vite build && gh-pages -d dist"`. If `npm run build` (the project's own typecheck-then-build script) is currently broken for unrelated pre-existing TypeScript errors, don't silently route `deploy` around it forever — flag that to the user as its own issue rather than treating "bypass tsc" as a normal part of this checklist.
4. Push the built `dist/` to a `gh-pages` branch (`npx gh-pages -d dist` handles this), then point the repo's Settings → Pages source at that `gh-pages` branch, folder `/ (root)`.
5. Re-run the deploy command after future changes — this isn't a one-time setup, `gh-pages` doesn't auto-run on push unless a CI workflow is added separately (and a CI-based build would need `lyra-ui` checked out in the runner too, since this app depends on it via a live sibling path alias, not a published package).

## Interaction/notification conditional behavior (if / then)

These are product-requested conditional behaviors layered into `AgentNextGenPage.tsx` (and, where noted, `../lyra-ui/src/components/create-new.tsx`). Each one was added for a specific reason and is easy to silently break during an unrelated refactor (this already happened once — see #5) — check this list before touching any of the related code, and update it when the underlying behavior changes.

1. **Select Channel — Voice disabled when already open.** If a contact already has an open Voice channel (`CreateNewOutboundContact.openChannelTypes` includes `"voice"`), the Voice option in `OutboundAddButton`'s/`CreateNew`'s `RadioButtonGroup` is disabled (`isChannelBlockedForContact`, `create-new.tsx`) — an agent can't have two simultaneous voice conversations with the same customer. `openChannelTypes` is type-presence only (not address-keyed) specifically because some open channels (e.g. a redialed call) have no recorded address value.
2. **Select Channel — skill selection survives a channel switch.** If the agent switches the selected channel and a skill was already chosen, keep it selected rather than clearing it, so "Start Interaction" stays enabled.
3. **Select Phone/Email — default to the directory primary.** If the contact has a `primaryPhone` on file (`CreateNewOutboundContact.primaryPhone`), default the field to it; only fall back to the first option in the list when no primary is set (`resolveOutboundDetailField`, `create-new.tsx`).
4. **Transcript content depends on `channelType`.** SMS/WhatsApp → the real mock conversation (customer name substituted in for the placeholder). Voice → "Coming Soon Voice Content". Email → "Coming Soon Email Content" (`InteractionTranscript`).
5. **Fresh vs. existing Chat/SMS/WhatsApp transcript.** If a Chat, SMS, or WhatsApp interaction was just launched by the agent (`Interaction.startedFresh`, set ONLY in the new-card branch of `handleStartCall`/`handleQuickDial`/`handleRedial`), show just the session-details separator with no messages (`isFreshTextLaunch` in `InteractionTranscript`, `channelType === "chat" || "sms" || "whatsapp"`). If instead the interaction came from re-selecting an existing card or opening an assignment notification (`handleOpenAssignmentFromNotification` deliberately never sets `startedFresh`), keep showing its full existing mock transcript. Getting this backwards (setting `startedFresh` from the notification handler too) is the exact bug that once blanked out Ethan Zhang's real conversation — don't reintroduce it. Originally wired for SMS only; broadened per an explicit bug report (a brand-new outbound WhatsApp was showing the full shared mock conversation instead of an empty one) — Chat and WhatsApp have the exact same "no history yet" reality for a freshly-launched card, so there was no reason the empty-transcript treatment stayed SMS-only. Voice/Email are NOT part of this — they always render their own fixed placeholder session (rule #27) regardless of `startedFresh`, so there's no "wrongly shows a full past conversation" failure mode for them to begin with. The synthetic fresh session's own "Channel" field (`freshSessionChannelLabel`) reads as whichever of the three was actually launched (SMS/Chat/WhatsApp), not a hardcoded "SMS".
6. **Notification titles are channel-aware.** Title is "New Email"/"New SMS"/"New Chat" depending on `NOTIFICATION_CHANNEL[notification.id]` (`channelNoun`/`newCaseNotificationTitle`). Escalations render as "Escalation - {Channel}". Sarah Miller's case is its own distinct `"new-agent-chat"` notification type (separate icon/color in `agent-notifications.tsx`), not a plain "New Chat".
7. **Customer Information panel opens at max width.** Initial `customerPanelWidth` is 425 (the panel's own `maxWidth` default), not `InteriorPanel`'s otherwise-lower fallback — passing a controlled `width` prop overrides that default, so this app has to match it explicitly.
8. **Activating any interaction exits Customer Information full screen.** If a new or reopened interaction is activated — via the top-left "+" Start Interaction button (`handleStartCall`), Quick Dial (`handleQuickDial`), Redial (`handleRedial`), or a new-assignment notification click (`handleOpenAssignmentFromNotification`) — while the Customer Information panel is full screen, it's forced back out (`customerPanelExitFullScreenSignal`, bumped at the end of each of those handlers, forwarded through `exitFullScreenSignal` to `InteriorPanel`) so the newly-opened interaction is actually visible instead of staying covered. Originally added for the notification path only; extend this to any future interaction-launch handler too, not just these four.
9. **Overview tab layout order.** The Latest Interaction + Latest Note column renders BEFORE Customer Overview in the JSX, which is what makes it sit to the left at full width and stack above Customer Overview once collapsed — pure flexbox DOM-order consequence (`.lyra-card-split`), not a separate ordering prop. Swapping the JSX order silently swaps the visual order too.
10. **"New Agent Chat" notification opens Agent Chat, not an assignment.** Clicking Sarah Miller's `"new-agent-chat"`-type notification does NOT go through `handleOpenAssignmentFromNotification` like `"new-case"`/`"escalation"` do — it switches the shared header panel straight from Notifications to Agent Chat (`handlePanelButtonClick("conversations")`, in `onNotificationClick`), since an agent-to-agent chat lives in that panel, not the interaction list. The "Conversations" header panel/button was renamed to "Agent Chat" (`PANEL_KEY_METADATA.conversations`, `contentByPanelKey.conversations`) to match.
11. **New Outbound's idle state shows favorites, scoped to whichever group is selected — never a blank body.** `OUTBOUND_CONFIG.hideContactList: true` (a prop on `../lyra-ui/src/components/create-new.tsx`'s `CreateNewOutboundConfig`) means "don't show the full unfiltered browse list by default," NOT "show nothing." With no search text: the `"favorites"`-kind group (rule #13, labeled "All") shows every favorited contact across every group; a `"contacts"`-kind group (Agents/Teams/Skills/Customers) shows only ITS OWN favorited contacts (a favorited agent shows up filtering by Agents, not by Teams) — per explicit request, filtering by Agents should show favorited agents, filtering by Skills should show favorited skills, and so on. Both cases are one `activeGroupContacts` computation in `create-new.tsx` — no separate blank-body render branch exists anymore (there used to be one; it was removed once idle states always had real, if possibly short, content to show). The empty-state message distinguishes "nothing favorited in this group yet" (`No favorited {label} yet`) from "no matches for this search" (`No matching {label}`) — don't collapse these back into one generic message. Default `false` on the shared prop itself, so every other `CreateNew` consumer (Storybook stories showing the full list) is unaffected.
12. **Typing a search query always shows the full match list, favorited or not.** The MOMENT `search.trim()` is non-empty, `hideContactList`'s idle-favorites-only scoping (rule #11) stops applying and the contact list + its `TableFooter` show every real match — `activeGroupContacts`/`filteredGroupContacts` in `create-new.tsx` already resolve to the right list for every state, so the render layer doesn't special-case "searching" vs. "not" at all anymore. Matching checks name, subtitle, `primaryPhone` (value or label), and `email` (`contactMatchesSearch`) — "a name, number, email" per explicit request. The `"favorites"`-kind group additionally widens its match pool to every contact across every group while searching (not just already-starred ones — see `activeGroupContacts`), so a search there can surface (and let the agent favorite) someone not yet starred; its placeholder is "Enter phone, email or search term" to signal this (`OUTBOUND_CONFIG`'s `all` group `searchPlaceholder`). A `"contacts"`-kind group's search stays scoped to that group's own contacts (Agents search doesn't pull in Teams). `OUTBOUND_CUSTOMERS` synthesizes a matching `email` (`splitCustomerName` + `${first}.${last}@example.com`, same formula `buildCustomerInfoFields` uses) so email search actually matches something for customers; agents/teams/skills have no email on file and simply never match that field.
13. **No standalone "Favorites" entry in the group dropdown — "All" is the default filter instead.** `OUTBOUND_CONFIG.groups`' first entry is now `{ id: "all", label: "All", kind: "favorites", ... }`, not `{ id: "favorites", label: "Favorites", ... }`, and `defaultGroupId` is `"all"` (was `"agents"`) — per explicit request, an agent no longer picks "Favorites" as one option among several; the favorites-idle/full-database-search behavior (rule #12) is just what "All" always does, and it's what New Outbound opens on by default. Still `kind: "favorites"` under the hood in `create-new.tsx` (that kind's behavior is exactly what's wanted) — only the id/label/default changed, not the shared component.
14. **New Outbound's search sits above the group filter, and changing the filter never clears it.** The search `Input` renders before the group `Select` in the outbound picker's header (`create-new.tsx`) — reversed from the original order. `setActiveGroup` (fired by the `Select`'s `onValueChange`) no longer calls `setSearch("")` — per explicit request, switching the filter should just re-filter whatever's already typed against the newly-selected group, not discard it. `pushScreen`/`popScreen` (real screen navigation, e.g. into/out of the call-setup detail screen) still clear `search` as before — only the in-place filter switch was changed.
15. **The pagination footer only renders while actively searching AND there are matches — never idle, never on a zero-result search.** The `TableFooter` condition in `create-new.tsx`'s popover `footer` is `screen.kind === "group" && ((activeGroup?.kind ?? "contacts") === "contacts" || activeGroup?.kind === "favorites") && !!search.trim() && filteredGroupContacts.length > 0` — both trailing clauses are per explicit request: `!!search.trim()` means an idle list of favorited contacts (whether a single group's own, or "All"'s cross-group set) doesn't get pagination chrome under it; `filteredGroupContacts.length > 0` means a search that comes back empty doesn't show a "Displaying 0-0 of 0"/"Page 1 of 1" footer either — in both cases there's nothing to page through, so no footer. The `"favorites"` half of the kind-check earlier fixed a real, shipped bug where the "All" group was excluded from this footer entirely (a leftover from when Favorites only ever listed a handful of already-starred contacts) — once "All" started searching across every group's ENTIRE contact list (rule #12), `pagedGroupContacts` silently truncated to the first `pageSize` (10) matches with no footer to page past them, reading as "All only searches Agents" (since `allOutboundContacts` concatenates Agents first) even though every group's contacts had actually matched underneath. The zero-matches empty message itself is a plain "No matches found" (`create-new.tsx`), not `No matching {label}` — "No matching all" read oddly since "All" isn't a noun a result set matches against. Any future change to which kinds get a real (possibly large) contact list must double check this condition covers them, stays gated on `search.trim()` for the idle case, AND stays gated on a non-empty result for the zero-match case — a match list with no way to page through it, showing pagination for a short idle favorites list, and showing pagination for zero results are three distinct mistakes this condition guards against at once.
16. **The detail screen's contact lookup must use `allOutboundContacts`, never `activeGroupContacts`.** `activeOutboundContact` (`create-new.tsx`) is the contact the "Select Channel"/"Select Phone"/"Outbound Skill" detail screen is showing — it's looked up by `screen.contactId` from `allOutboundContacts` (every contact across every group), NOT `activeGroupContacts` (the currently-VISIBLE, filtered-by-search-and-favorite-status list). This was a real, shipped bug: for the `"favorites"`-kind "All" group, `activeGroupContacts` only contains starred contacts once `search` is empty, and `pushScreen`/`goToDetail` (which navigate to the detail screen on a row click) unconditionally clear `search` — so clicking a NON-favorited contact found via search landed on the detail screen a render later with `search` reset to `""`, at which point that same contact had already dropped out of `activeGroupContacts`, and the lookup came back `undefined`. With no `activeOutboundContact`, the whole detail screen's content block doesn't render at all — just the footer's "Start Interaction" button, with nothing above it. `allOutboundContacts` is unaffected by search text, favorite status, or which group is selected, so this fixes it outright rather than special-casing one more way `activeGroupContacts` could exclude the very contact being viewed.
17. **"Continue with" ad-hoc contact when a search matches nothing but looks like a real email/phone.** In the "No matches found" case (rule #15's third state) specifically, if the typed query also passes `looksLikeEmail`/`looksLikePhoneNumber` (`create-new.tsx` — loose shape/digit-count checks, not real validation), an outline, full-width, `wrap`-variant `Button` (see rule #18) reading `Continue with "{query}"` appears below the message. Clicking it calls `handleContinueWithSearch`, which builds a throwaway `CreateNewOutboundContact` via `buildAdHocSearchContact` (`name` = the typed value itself, `channels: ["email"]` + `email` for an email query, `channels: ["voice", "sms"]` + `primaryPhone` for a phone query, `id` namespaced `adhoc:` so it can never collide with a real record), stashes it in its own `adHocContact` state, and navigates straight to the "detail" (Select Channel/Select Phone-or-Email/Outbound Skill) screen for it — same destination as clicking a real contact row. `activeOutboundContact`'s lookup (rule #16) checks `adHocContact` before falling back to `allOutboundContacts`, since this synthetic contact never lives in any real group's `contacts` list and would otherwise never be found there either. `resolveOutboundDetailField`'s email branch now prefers `contact.email` over its old unconditional `name`-based synthesis — required here specifically, since the ad-hoc contact's `name` IS the typed email address, and the old synthesis would have doubled it up into `jane@example.com@example.com`; this also incidentally fixed real customers' "Select Email Address" to use their actual synthesized email (`OUTBOUND_CUSTOMERS[].email`) instead of a second, independently-derived fake one.
18. **`Button` has a `wrap` variant for unbounded-length labels.** `../lyra-ui/src/components/button.tsx`'s `buttonVariants` gained a `wrap` boolean variant (default `false`, every existing button unaffected) — `wrap` overrides the base `whitespace-nowrap` behavior every button otherwise has with `whitespace-normal break-words text-center` and swaps the `size` variant's fixed height (e.g. `lg`'s `h-9`) for `h-auto` + `py-2`, letting the label wrap across multiple lines and the button grow to fit instead of silently overflowing its container on one line. First added for, and used by, the "Continue with" button (rule #17), whose label echoes back an arbitrary, unbounded-length typed search query. Reach for `wrap` on any future button whose label isn't a short, fixed, known-in-advance string — don't re-invent the same `h-auto`/`whitespace-normal`/`break-words` className combo by hand per call site.
19. **"Hide, don't destroy" — Dial Pad is hidden from the New Outbound filter dropdown, not deleted.** `OUTBOUND_CONFIG.groups`' every possible group now lives in its own named `OUTBOUND_GROUPS` constant; `OUTBOUND_CONFIG.groups` is `OUTBOUND_GROUPS.filter((g) => !HIDDEN_OUTBOUND_GROUP_IDS.includes(g.id))`, with `HIDDEN_OUTBOUND_GROUP_IDS` currently `["dialpad"]`. Per an explicit correction mid-task ("hide it don't destroy it") — a first pass deleted the `{ id: "dialpad", ... }` group entry outright; the fix keeps that group's full definition intact in `OUTBOUND_GROUPS` (`onQuickDial`/`handleQuickDial` also untouched), just excluded from what's actually handed to `CreateNew`'s dropdown. This is the general pattern for "remove X from the UI, but don't lose the ability to bring it back cheaply": a named source-of-truth list + a hidden-ids filter, not an outright deletion. Restoring Dial Pad is a one-line revert (drop `"dialpad"` from `HIDDEN_OUTBOUND_GROUP_IDS`), not re-authoring the group from scratch.
20. **New Outbound's search placeholder is one string for the whole flow, never per-group.** `CreateNewOutboundConfig.searchPlaceholder` (`../lyra-ui/src/components/create-new.tsx`, top-level, default `"Search..."`) replaced the old per-`CreateNewOutboundGroup.searchPlaceholder` field entirely (removed from that interface) — per an explicit, confirmed UX bug: `contactMatchesSearch` matches name/subtitle/phone/email identically no matter which group is selected, so switching the filter to e.g. "Agents" and having the placeholder change to "Search Agents" falsely implied the box now searched differently (name-only, or Agents-specific) than it did under "All" — it doesn't; the filter only narrows which contacts get checked, not what kind of query is accepted. `OUTBOUND_CONFIG.searchPlaceholder` is `"Enter phone, email or search term"`; no group in `OUTBOUND_GROUPS` sets its own anymore (the field no longer exists to set). Any future addition to `OUTBOUND_GROUPS` must NOT reintroduce a per-group placeholder — if the search's actual matching behavior ever genuinely differs per group, that's a signal to reconsider this rule, not to route around it with a group-level override.
21. **Message-bubble hover toolbar (Copy/Add tag) is bare icons, not a boxed toolbar — and the tag popover must not auto-focus its trigger on close.** Per explicit request, the wrapping `div` around the Copy `ActionIconButton` and `TagPicker` in `TranscriptMessageBubble` lost its box chrome (`rounded-lyra-md border ... bg-lyra-bg-surface-base ... shadow-sm`) — just the two icons fade in on row hover now, no surrounding pill/panel. That wrapper is also `pointer-events-none` while faded out (`opacity-0`) and only `pointer-events-auto` once actually visible (hover or the tag popover open) — otherwise the invisible icons underneath still receive hover/focus, and each one's `Tooltip` (`Button`'s `isIconVariant && title` wrap) can pop open pointing at nothing. Separately, `lyra-ui`'s `TagPicker` (`tag-picker.tsx`) passes `onCloseAutoFocus={(e) => e.preventDefault()}` to its `Popover` — Radix's default behavior returns focus to the trigger when a popover closes, which would hand focus back to the (Tooltip-wrapped) tag icon the moment its "Add tag" flyout is closed and pop that tooltip right back open with no real hover behind it, left dangling. Both fixes are about suppressing *unintended* tooltip pop-opens from stray hover/focus, not about the tag-picker's own popover behavior, which is unchanged (still opens on click, still lets more than one tag be picked per open) — only the tag PILLS inside that popover render inline/wrapped (`flex flex-wrap`) now instead of one per row, per a separate explicit request.
22. **New messages auto-scroll the transcript, with different rules for the agent's own message vs. the simulated customer reply.** A `useEffect` keyed on `liveMessages.length` (`InteractionTranscript`) checks that array's own last entry: if it's the agent's own just-sent message (`sender === "agent"`), it ALWAYS smooth-scrolls to the bottom — regardless of where the agent had scrolled to — since they just took an action in this conversation and should see it land, same as clicking "Scroll To Latest" (`scrollToLatest`) themselves; it also resets `isAtBottom` to `true` so the customer's reply a couple seconds later keeps auto-scrolling right along with it too. If the last entry is instead the simulated customer reply, it only scrolls if the agent was already caught up to the bottom (`isAtBottomRef.current`, a ref mirroring `isAtBottom` state — read fresh rather than depended on, so this effect isn't keyed on every `isAtBottom` flip, only on an actual new message arriving) — if they'd scrolled up to read earlier messages, an incoming reply lands without yanking their position back down; that only resumes once they scroll back to the bottom themselves (`handleTranscriptScroll`) or click "Scroll To Latest". Keyed on `liveMessages.length` specifically (a primitive), not the `liveMessages` array reference itself — `activeInteraction.liveMessages ?? []` at the call site is a fresh `[]` every render an interaction has no live messages yet, which would otherwise re-fire this effect on every unrelated re-render (e.g. the shared clock tick).

Deliberately `undefined`, not `0`, for Voice/Email: those sessions only ever hold a placeholder `messages: []` (see `TRANSCRIPT_SESSIONS_VOICE`/`_EMAIL`'s own doc comment — there's no real per-message transcript UI for a call or an email thread), so showing "0 Messages" there would misreport a call/email as an empty chat rather than the prop simply not applying to that channel type. `isTextChannel` (`channelType === "chat" || "sms" || "whatsapp"`) was extracted as its own const specifically so this call site and the pre-existing `isFreshTextLaunch` computation share one source of truth for "is this a chat-shaped channel" instead of duplicating the three-way OR.

31.6. **`KebabMenuButton` (`../lyra-ui/src/components/kebab-menu-button.tsx`) now forwards arbitrary extra props onto its own trigger element — needed for it to work as the direct child of a `Tooltip`.** The "More Options" tooltip added to `ChannelRow`'s kebab (rule #30's area) silently never appeared on hover. Root cause: `Tooltip`'s `TooltipPrimitive.Trigger asChild` clones whatever single child it wraps and injects its own hover/focus-tracking props (`onPointerEnter`/`onPointerLeave`/`onFocus`/`onBlur`, plus a composed `onClick`) directly onto it — for a plain DOM element that's automatic (React merges cloned props straight onto the tag), but `KebabMenuButton` is a custom component whose function signature only ever destructured its own known prop names (`items`, `ariaLabel`, `className`, `as`, `icon`, `align`, `onOpenChange`, `badge`) and dropped everything else — so Radix's injected handlers landed on the prop object and were silently discarded, never reaching the actual `<button>`/`<span>` Radix needed to attach listeners to. Fixed by extending `KebabMenuButtonProps` with `Omit<React.HTMLAttributes<HTMLElement>, "children" | "className" | "onClick">`, destructuring the rest (`...rest`) and spreading it onto the internal trigger element, with `onClick` still composed explicitly (calling the incoming handler, THEN this component's own `stopPropagation()`) rather than just spread, since it already has its own required behavior to preserve. This is a general fix to the shared component, not a `channel-row.tsx`-specific patch — any other `KebabMenuButton` usage that wraps it in a `Tooltip` (or any other Radix `asChild`-based primitive) gets the same fix for free.

31.5. **The elapsed clock+time moved off the chip row entirely, onto the preview/skill-name line below it — which is what finally ended the whole "timer collides with the Consult/Transfer + Outcome buttons" saga (rules #55/#56 and their several follow-up passes).** `../lyra-ui/src/components/channel-row.tsx`'s `ChannelRow` used to render the elapsed-time text on the SAME row as the chip and the button cluster, which is exactly why so much CSS (a `relative flex-1` anchor, `min-w-0`/`overflow-hidden`/`whitespace-nowrap` truncation, a `group-hover:pr-12` reserved-space hack) existed just to make that text clip instead of visibly bleeding out from behind the transparent ghost buttons on a narrow row. Per explicit follow-up ("what if we moved the timer to the right of the skill name row"), the top row now only ever contains the chip and the button cluster (`ml-auto`, no longer sharing space with anything else, no `flex-1` spacer needed) — removing the possibility of that collision altogether, since the chip+cluster together never come close to running out of room. The elapsed clock+time renders on the SECOND row instead, next to (not floated away from) the preview/skill-name text — a further follow-up rejected floating the timer to the row's far right in favor of it just sitting immediately after the preview text in normal flow. That second row is now unconditionally rendered (previously gated on `preview` being present, since `preview` is optional but `elapsed` never is): `preview`, when present, is the `min-w-0 flex-1 truncate` item (gives up width first on a narrow row), and the elapsed-time span is `shrink-0` (never truncates, always fully readable) — when `preview` is absent, the timer is simply the first and only item on that line, sitting at the same left edge the preview text would have occupied rather than being centered or pushed anywhere. On a very narrow row, the button-cluster overlay CAN now visually land on top of the chip instead (nothing else left for it to collide with) — accepted, since avoiding that was the entire point of this move.

31. **Notifications is unpinnable like every other app-header panel now, and "View All Apps" surfaces the unread count once it's the one thing hiding it.** Notifications used to be the one `PanelKey` forced permanently pinned — `PanelPinButton`'s row for it in the "View All Apps" menu (`appsMenuItems`, built from `PANEL_KEY_METADATA`) had `disabled={key === "notif"}`, a hardcoded `pinnedLabel` explaining why, and its pinned-icon/className overrides both excluded `key === "notif"`. Per explicit request that special-casing is gone: `pinnedKeys.notif` toggles through `PanelPinButton` exactly like every other key, and unpinning it just stops `NotificationsBell` from rendering in the header icon row — already true for free, since that row was always `panelOrder.filter(showHeaderIcon).map(...)`, and "notif" only ever passed `showHeaderIcon` because `pinnedKeys.notif` was hardcoded `true`. The risk this raises: unpinning (or responsively auto-hiding, same `showHeaderIcon` gate) Notifications also hides its own badge — the only place an unread count was visible — silently making new notifications invisible. Fixed by giving `../lyra-ui/src/components/kebab-menu-button.tsx`'s `KebabMenuButton` a new `badge?: number` prop, reproducing `Button`'s own badge overlay (button.tsx: `relative inline-flex` wrapper + `Badge shape="circle" variant="critical" size="sm"` positioned `absolute -top-2 -right-2`) rather than composing `Button` itself, since this trigger is its own hand-rolled `<button>`/`<span>` (not built on `Button` — see the file's own class comment on why). The "View All Apps" `KebabMenuButton` passes `badge={!showHeaderIcon("notif") ? notifications.filter((n) => !n.read).length : undefined}` — only shown while the header ISN'T already displaying that same count via `NotificationsBell`'s own badge, so an unread count never appears twice at once.

    These two buttons don't sit inline as flex siblings (that squished the row — chip + clock + 2 buttons + kebab all fighting for width). Instead they're a hover-only overlay: `pointer-events-none opacity-0` + `group-hover:pointer-events-auto group-hover:opacity-100` on the row's own `group`, `absolute` positioned so they cost nothing in the flex layout while hidden. Two wrong anchors were tried before landing on the right one: (1) `inset-0` on a wrapper sized to just the clock+time text squeezed the two icon-sm buttons to fit that narrow box via flex — same squish bug, now only on hover; (2) `inset-y-0 left-0` fixed the squeeze but pinned the buttons to always start exactly at the clock icon's position, so hovering always covered the timer regardless of whether there was room elsewhere. The fix: merge the separate `flex-1` spacer that used to sit between the clock+time span and the kebab into the SAME relative wrapper as that span (now `relative flex flex-1 items-center`, spanning the full width from the clock through to just before the kebab), and anchor the overlay `inset-y-0 right-0` instead of `left-0` — floating the two buttons flush against the kebab. Because the clock+time text is left-anchored and the buttons are right-anchored within one shared `flex-1` span, they only visually overlap when the row is too narrow for both — wide rows show the timer clear with the buttons floating in the empty space beside it; narrow rows let the buttons cover the timer on hover instead of wrapping or squishing. Pure CSS, no JS collision detection.

    A further follow-up: on an inactive/non-highlighted row the buttons still rendered visibly shorter than their real 24x24 `icon-sm` size — a second, distinct squish bug from the two above, this one about HEIGHT rather than width. Root cause: the shared `relative flex-1` anchor had no explicit height, so its height came from its only in-flow child — the clock+time text (`lyra-body-xs`'s own line-height, well under 24px). The overlay is `absolute inset-y-0`, and per the CSS spec, an absolutely positioned box with both `top`/`bottom` set and no explicit height of its own gets its height computed directly from its containing block's height — it does NOT expand to fit its own children the way normal flow would. So the overlay was inheriting that sub-24px height from the text and squeezing the two `icon-sm` (24px) buttons down to fit, instead of them rendering at their true size. Fixed by adding `h-6` explicitly to both the anchor span and the overlay div, giving `inset-y-0` a full 24px containing block to size against — matching the buttons' own `icon-sm` size and the kebab's own fixed `h-6 w-6`, so all three now sit at a consistent, unsquished 24x24 regardless of row/highlight state.

    A first pass rendered these two buttons as ordinary flex siblings next to the elapsed-time text and the kebab — always visible, taking up real row width. Per explicit follow-up (a screenshot showing the whole row squished — chip, clock, two buttons, and the kebab all fighting for one line), they're now a HOVER-ONLY overlay instead: the elapsed clock+time `<span>` is wrapped in a `relative inline-flex` anchor (`inline-flex`, not a plain inline `span` — an inline box is an unreliable containing block for an `absolute inset` child), and the two buttons render on an `absolute inset-y-0 left-0` layer on top of it, `pointer-events-none opacity-0` until the row (`group`, on the row's own outer div) is hovered (`group-hover:pointer-events-auto group-hover:opacity-100` — same "invisible-but-still-eats-hover-without-pointer-events-none" fix `AgentNextGenPage.tsx`'s message-bubble hover toolbar already uses). The overlay's own background matches whichever the row's current background actually is (`highlighted ? "bg-lyra-status-info-subtle" : "bg-lyra-state-hover"`, mirroring the row's own wrapping `className` condition) so it genuinely covers the clock/time text rather than letting it show through underneath. Deliberately `inset-y-0 left-0`, NOT `inset-0` — two `icon-sm` buttons are wider than most "MM:SS" labels, and stretching the overlay to exactly the anchor's own (narrower) width would squeeze them via `flex`, reproducing the exact same squished look on hover instead of always; left-anchored with natural width instead, freely extending into the (empty, same-colored) `flex-1` spacer if it needs to. Being `absolute` (out of flow) is also what makes this "cost nothing" layout-wise — hidden, the clock/time span (and the spacer and kebab after it) lay out exactly as if these two buttons didn't exist, which is what keeps the kebab pinned at one consistent position regardless of whether they're showing, per that same explicit follow-up ("keep the kebab menus aligned").

## AI-led cases (Lucas Thomas / Marcus Webb pattern) — follow these when building any new scripted AI case

Reference implementation: the Lucas Thomas case on the Advanced page (`agent-next-gen-lucas-thomas-scenario.ts`, `agent-next-gen-lucas-thomas-panels.tsx`, `agent-next-gen-transcript.tsx`, `AgentWorkspaceAdvancedPage.tsx`). Marcus Webb's patterns (`MarcusWebbAiChatBubble`, `ActionLogNoteEntry`, `NextBestActionOptionPicker`) are references to reuse, not code to import wholesale.

**Architecture**
- Keep each case data-driven: one scenario file (transcript, initial message count, realtime steps with typing times, decision follow-ups, panel keys, chip link/replacement maps) plus a separate panels file for side-panel bodies.
- Setup messages are already on screen at launch; later messages play live (timeouts + typing indicators). Include a "Chat started" event at the top and hide the mock follow-up messages.
- Side panels are native to each customer: panel state is stored per interaction, never carries over to another customer, and the chat is never shown inside a side panel.
- Use lyra-ui components and type classes (`lyra-body-md`/`-sm`/`-lg-emphasis`, `Accordion`, `Tag`, `Badge`, `Button`, `Spinner`, `ToggleGroup`, `AIInput`) — no oversized custom text.
- Tailwind `/alpha` on bare lyra color-variable tokens generates no CSS; use `color-mix(in srgb, var(--token) N%, transparent)`.

**AI chat appearance**
- AI messages float LEFT in purple (`bg-lyra-accent-purple-soft`); only the human agent floats right. AI avatar = purple `#6149C1` circle with the `Bot` icon (lyra-ui `ChatMessage` `ai` prop).
- Show a typing indicator before every non-initial message (AI variant: left aligned, purple dots); animate new messages in with `animate-in slide-in-from-bottom-4 fade-in-0 duration-200`.
- Event lines (e.g. "Launch price held") are plain text lines, not tags.
- Before takeover: chat in review mode (warning ActionBar + Takeover button), no SLA warning; Takeover starts the SLA clock and the AI sends a warm handoff message (typing dots first) saying the customer is being transferred to the human agent.
- Hide the channel icon / chat-active icon; hide the unassign/dismiss icons in the left-nav card and session row; lock Outcome (and kebab) in the left-nav card until takeover via `controlsDisabled`.

**Interstitials (agent actions logged in the chat)**
- A bordered clickable row: note icon, title, time, actor (John Smith or Checkout AI Agent), chevron; clicking opens a side panel. Add one whenever the agent acts: approve, decline, something else, and every Ask Copilot question or chip.
- First show "AI agent is performing this now…" with a spinner (~1.8s), then replace it with the row alone — do NOT show an "AI agent finished performing this" line.
- The row whose panel is open gets the selected look (`border-lyra-border-active bg-lyra-status-info-subtle`); clicking it again closes the panel.
- Chip rows reopen the chip's own panel; typed free-form questions open the instruction panel with a "Copilot result" card and auto-open when finished.
- Every panel the agent opens is added to the Artifacts card in Contact Details as a re-open link (Experience Memory excluded); "View All" appears only above 10 and opens an Artifacts list in the docked panel with a back arrow to Contact Details.

**Approval request box**
- Header: light blue (`bg-lyra-status-info-subtle`), sparkle icon, "Approval request · {agent}" + time, "Copilot summary" + chevron; animates open/closed.
- Content: headline, description, checklist (green checks for done items; the pending item amber with a "Needs a person" badge) on the left; Experience Memory bullets + sentiment bars on the right. Checklist titles are links that open Experience Memory in the docked side panel with the matching event expanded.
- White bordered areas inside the card, lyra type sizes. Collapsing hides only the summary — while a decision is pending the "How would you like to proceed?" footer stays visible.
- If the agent takes over before deciding, the options go away and the footer says "Agent has taken over the chat".
- A case can raise a second approval later; give each card distinct option values so one handler serves both.

**Autosummary / Contact Details**
- Autosummary headings are light blue (`autosummaryBlue`: `bg-lyra-status-info-subtle`, blue icon), not a "Needs a Person" tag. In summaries, `[label](key)` creates links that open interior slide-out panels.
- Real-Time Summary, customer card (subtitle + tags), `detailedSummary` and `snapshot` must reflect the case itself — override them per case in `customerContextOverviewInfo`, never the generic hashed profile.
- "View Experience Memory" under the Real-Time Summary swaps the docked panel to Experience Memory (back arrow, customer name, "Experience Memory" subhead). Orders opened from Experience Memory have no back arrow in the slide-out; orders opened from Purchase history keep theirs.

**Approve / Decline / Something else**
- Approve the Exception reveals a white bordered content area (headline, description, Experience Memory line, card of what will happen, optional knowledge-article row) with a confirm button (e.g. "Authorize and Place Order") — it does not perform immediately.
- Decline requires a reason in a note box.
- Something else = free-text instruction plus small purple pill chips (sparkle icon on the left). Lookup chips show a spinner then open an interior panel; a used chip is removed and replaced by a related one (e.g. Show purchase history → Check fraud screening results); other chips just fill the box.
- After submit the card shows a green check + result line; the automation plays out in the chat, outside the card: instruction row, events, then the AI messaging the customer.
- Resolved paths end with a Wrap up card (same accordion shell as the approval request, success-subtle header, summary, disposition line, "Complete wrap-up" button); completing it saves the outcome and closes/unassigns. If the customer follows up, keep the chat open and have the AI reply instead of auto-closing.

**Chat input / Ask Copilot**
- A lyra-ui `ToggleGroup` (not tabs): "Chat with Customer" / "Ask Copilot"; one mode always active; switching focuses that mode's input; both panes share one grid cell so the height never changes; the chat draft is kept.
- Ask Copilot uses `AIInput` with purple pill suggestion chips beneath it. A chip in the Approval request box and the same chip in Ask Copilot must open the same panel, add the same chat row, and reopen the same content. Anything asked of Copilot is logged in the chat as an interstitial.

- After every edit run `npx tsc -b --noEmit` here (baseline 4) and `npx tsc --noEmit` in `../lyra-ui` (baseline 3); don't fix baseline errors unless asked. Say honestly when nothing was verified in a browser. Don't commit unless asked.
