# Agent Workspace Simulation — Consolidated Plan

**Target repo:** `~/GitHub-Local/agent-next-gen-demo` (consumes `~/GitHub-Local/lyra-ui` through the Vite source alias; design-system changes land in lyra-ui, app changes land here).

All client-side. The provider layer keeps a real backend (Twilio, CXone ACD) a swap rather than a rewrite; the profile layer keeps a new vertical a data pack rather than a code fork. Step prompts for executing this plan live in PROMPTS.md.

## Phase 0 — Provider architecture and simulation plumbing

1. **Domain model.** App-owned types — `Interaction`, `Message`, `Utterance`, `Entity` (the vertical's primary record: customer/patient/account holder), `RelatedRecord`, `AgentState` — with vendor-agnostic IDs plus an `externalId` slot. Vendor payloads never reach components.
2. **Four provider interfaces** (`src/providers/`, types only). `InteractionProvider` (events: `incoming`, `stateChanged`, `message`, `transcript`, `typing`, `ended`; commands: `accept`, `decline`, `end`, `hold`, `mute`, `transfer`, `sendMessage`, `setTyping`, `dial`, `setAgentState`, `connectAgentLeg`, `disconnectAgentLeg`, `associateEntity`, `setCaseStatus`, `completeWrapUp`, `setRecording`, `setMasked`, `sendDtmf`; reads including `listPresenceOptions` and `listOutboundSkills(channel)`; a `capabilities` map covering hideable UI controls). `MediaProvider` (`unlock`, volume, `audioStateChanged`/`speaking`/`wordBoundary`; no `speak`). `CustomerDataProvider` (`getEntity`, `search`, `findNearMatches`, `create`, `update`, `linkContactMethod`, `getContactHistory`, and a generic `getCollection(name, query)` behind named convenience methods). `AssistProvider` (`suggest`, `extractEntities`, `cancel`; cards and extracted fields arrive as events). All methods async and reject only with `ProviderError` (`not-supported` | `invalid-state` | `not-found` | `network`); all state changes arrive as events.
3. **Provider context.** Supplies the active provider set, the active database handle, and the active `ContactCenterProfile`; chosen by `?provider=sim|twilio|cxone`. UI hides controls a provider's `capabilities` doesn't include.
4. **`SimulatedInteractionProvider`** in `src/adapters/sim/`. A pure client talking over a `SimTransport` (`BroadcastChannel("agent-sim")` today, swappable for WebSocket later) to an in-window `SimEngine` that owns state and scripted timers, with configurable injected latency so the UI is built for a real network from day one. Dev-only `window.__simCustomer` stands in for the customer console until step 6.
5. **Migrate existing simulation behind the provider.** Incremental: new flows first, existing paths after.
   - **5.0 Interaction store + view-model adapter.** A store in `src/provider-context/` that subscribes to the active `InteractionProvider`, hydrates via `getSnapshot()`/`getTranscript()`, upserts snapshot events by id, and exposes hooks (`useAgentState`, `useInteractions`, `useInteraction`, `useTranscript`); plus a pure adapter that groups domain Interactions by `journeyId` into the pages' existing left-nav card view model. Prerequisite for every migration below.
   - **5a Agent leg.** The agent-leg `setTimeout` connect sequence and the in-memory leg-state module move onto `connectAgentLeg`/`disconnectAgentLeg`; also authorizes a backward-compatible lyra `AgentProfile` change (optional controlled leg props).
   - **5b Dial pad / interaction creation** through `dial`.
   - **5d Voice bar, incoming tile and wrap-up onto the provider.** Hold/mute/record/mask/keypad, hang up, Accept/Decline, the session status pill (`setCaseStatus`), and the Outcome popover / Wrap-up card (`completeWrapUp`).
   - **5c Scenario player; retire page timers.** Marcus Webb scenario timers move into the engine's scenario player. Runs after step 7.
6. **Customer console route.** `#/customer-console`, same Vite app, talks only to the sim provider — the agent UI never knows it exists. Replaces `window.__simCustomer`. Handshake: attach to an existing interaction or create one ("Start inbound chat/call as <entity>" or "as unknown caller" with free phone/name entry), carrying identifiers (ANI, email, chat handle) and pre-contact context.
7. **Scenario script format** (runs before 5c). TS/JSON canned lines per entity per channel, expressed as `SimCustomerAction`-compatible steps; loaded from the active profile; Marcus Webb ported as data.
8. **Contract test suite** (pulled forward before the 5.x migrations). `describeInteractionProviderContract(label, factory)` (`src/contract-tests/`), runnable against any `InteractionProvider`: the incoming → accept → message → hold → end → completeWrapUp lifecycle (chat and voice), outbound dial, typing both ways, ack-before-event ordering, idempotent no-op commands, `not-supported`/`invalid-state`/`not-found`, every ended reason through wrap-up, and `dispose()`. Also covers the provider-cache lifecycle. Run with `npm test` (Vitest). **This suite is the bar every adapter must pass.**

## Phase 1 — Vertical profiles and database management

1. **`ContactCenterProfile` type and registry.** Each profile declares terminology (entity name and labels), schema (entity fields + related collections with their status vocabularies), generators, scenario scripts, an intent pack (Tier 1 patterns/slots, Tier 2 tools and system prompt), compliance behaviors, dispositions/reason codes, and a handoff-snapshot template.
2. **Verticals.** Build fully: retail/e-commerce (orders, returns, loyalty, payments), collections (debts, payment plans, promises-to-pay, contact attempts), healthcare (appointments, claims, prescriptions, providers), customer service/tech support (tickets, entitlements, devices, known issues). Thinner packs on the same engine: banking (accounts, transactions, cards, disputes), telecom (lines, plans, devices, outages — the current Marcus Webb data lives here), insurance, travel/hospitality, utilities.
3. **Generator engine.** Shared deterministic synthetic-data engine; per-vertical generators with realistic distributions and status mixes (payments mostly succeeded, some declined, occasional refund; claims with denials; tickets across states), plus showcase records guaranteed to make demo questions land — Marcus Webb gets at least five declined payments.
4. **Named databases on IndexedDB (Dexie).** `SimulatedCustomerDataProvider` takes a database handle; create, switch, export/import as JSON, reset to demo.
5. **Create-database wizard.** Pick vertical → name → size and history depth → seed → optional file import → generate → connect.
6. **Vertical-aware import.** `.csv`/`.xlsx` in-browser (PapaParse / SheetJS), column mapping onto the selected profile's schema, preview, validation, dedupe; extra sheets map onto related collections.
7. **Schema-driven panels** — the real work of this phase. Customer Profile card, Details-panel accordions, and the transactions panel become generic entity + related-collections renderers driven by the profile's schema; the current hard-coded layout survives as the telecom profile's rendering.
8. Route `buildCustomerContextOverviewInfo`, contact history, the dial pad, and the console picker through the provider and profile. Marcus Webb becomes a scenario inside the telecom pack rather than a special case.

## Phase 2 — Realtime chat simulation

0. **Render performance pass.** Profile which components re-render on a single provider event and why (React Profiler / dev timing hook); smallest fixes (memoized selectors in the store hooks, `React.memo` on heavy subtrees, state splitting). No visual changes; target under ~50ms per event.
1. Console chat view: thread (lyra-ui `chat-message`/`conversation-message`), composer, typing toggle, canned lines from the active profile, "End chat."
2. Agent app: `incoming` event for chat creates an inbound interaction via the existing channel-row / interaction-nav flow; messages append; the agent composer calls `sendMessage`; typing both ways.
3. **Unknown-contact state.** No match on the handshake identifier → Profile card shows "New <entity>" with the handle; handoff snapshot says no prior history; an empty "Draft <entity>" card appears in the AI-assist slot, fields from the profile's schema.
4. Handoff snapshot card (former Next Best Action): seeded from pre-contact context through the profile's template; static once the agent takes over.
5. Expose `onCustomerUtterance` / `onAgentUtterance` from the provider's transcript events. Nothing listens yet.

## Phase 3 — Voice call simulation

1. **`SimulatedMediaProvider`.** `MediaProvider` has no `speak()`: the sim media provider subscribes to transcript events itself and drives TTS from them. TTS via `speechSynthesis` with a voice per persona; optional agent-side `SpeechRecognition` (Chrome) while unmuted, with typed agent lines on the console as fallback.
2. Console voice view: composer, canned lines, voice/rate/pitch, "Hang up."
3. Inbound ringing via the provider's `incoming` event drives the existing incoming-call UI; Answer is the audio-unlock gesture.
4. Playback: `transcript` events append to the transcript and queue TTS (no overlap); audio stops when the interaction's state leaves `active`/`held` (the move to wrap-up or ended), not on `ended`, which can fire long after the call dropped; pause/resume on `hold`.
5. Realism: `onboundary` reveals words in sync with audio; `onstart`/`onend` drive the "customer speaking" indicator in the voice call controls.
6. Same unknown-contact state as chat; speech normalizers for emails ("dot"/"at") and spelled-out names.

## Phase 4 — AI assist, Tier 1: deterministic and grounded

1. **`SimulatedAssistProvider`, router half.** Loads the active profile's intent pack: `{ patterns, slotExtractor, collection, query, card }`; runs on every utterance and on agent-initiated asks.
2. **Generic parameterized handlers.** One engine — `getCollection(name, { status?, limit?, sort?, since?, until?, minAmount? })` — with filter/sort executed in code; vocabulary comes from the profile, so "last 5 declined payments" and "last 3 denied claims" are the same code path.
3. **Slot extraction.** Counts, the profile's status vocabulary, recency, date phrases, amounts. "Show me the last 5 declined payments" → `{ status: "declined", limit: 5, sort: "newest" }`. Unfilled slots defer to Tier 2 rather than guess.
4. **Cards render records, not prose.** Cards arrive as `AssistProvider` `card` events (successive full snapshots). Title restates the interpreted query; body is the actual table; a provenance line names the collection.
5. **Compliance gates in front of cards.** Added to the `AssistCard` contract in this step (deliberately left out of P0.2). Healthcare: nothing PHI-bearing renders until the agent marks identity verified ("Verify identity to view"). Collections: right-party verification and a mini-Miranda reminder card at call start, promise-to-pay capture. Banking: card numbers masked, tying into the existing Mask control.
6. **Placement per channel.** Voice — inline overlay in the main contact container, expands in place. Chat — composer-adjacent suggestion strip, never interleaved into the thread. Expanded state reuses the Details-panel Accordion/card treatment.
7. **Actions map to the app.** "View full history" opens the related-records panel; "Open case/ticket/claim" jumps to it.
8. **Agent ask box** on lyra-ui `ai-input`/`ai-panel`/`ai-process`; same router, same cards.
9. **Progressive entity creation, deterministic half.** Regex extractors for email, phone, ZIP, account/member number, amounts, name heuristics; detected values arrive as `AssistProvider` extracted events and fill the Draft card live, each tagged with its source utterance. Before save, `findNearMatches` offers "Link to <existing>?" vs "Create new." Agent saves with one click or edits; the AI never writes silently. Interaction ended without saving → auto-save flagged *provisional*. On save, the interaction re-associates and Profile/Snapshot/history/table update live; expanded state reuses the existing create form, fields from the profile's schema.
10. No-match fallback: nothing (voice) or a quiet "I can look up <collections>…" hint (chat), listing what the profile actually has.

## Phase 5 — AI assist, Tier 2: a real model with tools

1. **Model access** inside `AssistProvider`: a ~30-line proxy holding the key, direct browser calls behind Anthropic's explicit opt-in header (localhost only), or a local model via Ollama.
2. **Tools and persona from the profile.** The generic collection query exposed with the profile's schemas; `propose_entity_fields` for conversational addresses, employers, contact preferences, reason-for-contact — feeding the Draft card with the same confirm-before-save rule. System prompt carries the vertical's persona and compliance rules.
3. **Hybrid rule.** Retrieval stays on the Tier 1 router; the model does synthesis only — "summarize why she's frustrated," "draft a reply offering the credit," "what next" — with Tier 1 results as context, never answering a data question from its own head.
4. **Streaming** into cards; **conversation context** (last N utterances + handoff snapshot) per request.
5. Replace Phase 4's no-match fallback with a Tier 2 call.

## Phase 6 — Virtual agent and escalation to a human

A bot handles the contact first; the customer gets irate or asks for something beyond the bot's authority; the bot escalates, and the human agent takes it over in the app with the whole history in front of them. Both sides of the bot segment are model-driven — no scenario script plays either the customer or the bot (P0.7 scripts remain the console's manual canned-lines panel only). Depends on chat (Phase 2), voice (Phase 3), the handoff snapshot (P2.4), the console (P0.6) and model access (P5.1), so it runs after Phase 5.

1. **Domain and contract.** `Interaction.origin` gains `"escalated"`. `Interaction.escalation?: { at, reason: "customer-requested" | "out-of-authority" | "sentiment" | "bot-uncertain", summary, intent, sentimentTrend, botAttempts[], pendingRequest? }` is written by whoever ran the bot segment and is the only thing the human-side UI consumes. `Message`/`Utterance` get `author: "customer" | "agent" | "bot"` (today's two plus bot); the bot segment is the same Interaction's transcript up to `escalation.at` — same `InteractionId`, same `journeyId`, no second contact. New **`BotAgentProvider`** contract in `src/providers/` (types only): `handle(interactionId)`, `onCustomerTurn(turn)`, `release(interactionId)`; events `botTurn`, `thinking`, `escalate`, `released`; `ProviderError` only; `capabilities` for channels and `canEscalate`. The bot converses and *asks* to escalate; routing stays with the engine (or a real ACD). `ContactCenterProfile` gains a **bot pack**: persona, authority (what the bot may approve, with limits), escalation policy (which triggers apply and their thresholds), and the bot's tools over `getCollection`. Contract tests: `describeInteractionProviderContract` gains "an escalated `incoming` carries `escalation` and `getTranscript` returns the bot segment", gated on a new `InteractionProvider` capability `escalation` so an adapter with no virtual agent skips it per the going-real rule; new `describeBotAgentProviderContract` (turn ordering, escalate fires at most once, `release` cancels in-flight work, `not-supported` gating).
2. **Simulated bot.** `SimulatedBotAgentProvider` in `src/adapters/sim/` on the P5.1 model backends (backend selection lifted into a shared module if it still lives inside the assist adapter). System prompt = the profile's persona, authority and compliance rules; tools = the profile's collection query plus `escalate(reason, summary)`. **Bot-first routing** in `SimEngine`: a console-started contact flagged bot-first is handed to the bot; `escalate` moves it to the queue and the agent app receives `incoming` with `escalation` populated and the bot transcript already in place. The engine honors an explicit "I want a person" even if the model misses it (policy guard, not a script). Chat first.
3. **Console AI-customer mode.** Beside typed and canned lines, "Play as <entity>": a model-driven persona built from the entity record and contact history plus a goal and temperament chosen on the console (refund over the bot's limit, rising frustration, …). It emits ordinary `SimCustomerAction` messages, so the engine can't tell it from a typed customer. During the bot segment the console voices both parties with its own TTS — no agent is on the contact yet.
4. **Agent-side handoff.** Incoming tile shows "Escalated from virtual agent" with the reason; accepting loads the transcript with bot turns rendered distinctly and a handoff divider at `escalation.at` (lyra transcript edit authorized); the handoff snapshot (P2.4) is seeded from `escalation` through the profile's template, then frozen; AI assist resumes over the full transcript. Built once in the shared contact-handling code and consumed by both pages (parity decision). Accept drops the whole bot segment into the transcript at once — a browser check against P2.0's budget.
5. **Voice.** Same path on voice: the bot segment is voiced on the console; on Answer the console stops the bot's voice and `SimulatedMediaProvider` takes over the customer's voice mid-call on the same Interaction, with no re-ring.

## Going real later — what each seam swaps to

`InteractionProvider` → CXone Agent API event stream + actions, or Twilio TaskRouter + Voice/Conversations. `MediaProvider` → CXone integrated softphone or Twilio Voice SDK. `CustomerDataProvider` → a CRM or your own API, with the profile's schema as the mapping target — AI grounding and schema-driven panels come along for free. `AssistProvider` → a server-side service or vendor copilot. `BotAgentProvider` → a hosted conversational agent (ElevenLabs Conversational AI, Vapi, Retell, OpenAI Realtime) behind a thin adapter — or nothing at all when the ACD's own virtual agent (CXone Virtual Agent Hub, Twilio Studio) runs the bot segment server-side, in which case the only requirement is that the `InteractionProvider` adapter populates `escalation` and the bot-authored transcript on `incoming`. Auth, tokens, and webhooks live inside the adapter; the browser-side contract doesn't change. An adapter counts as done only when it supplies an `InteractionContractHarness` (its provider, plus a `customer` driver backed by a fake vendor backend) and passes `describeInteractionProviderContract` under `npm test`; it may skip a test only where its own `capabilities` say the feature is off. Transfer/consult semantics, ACW/disposition, and WebRTC setup will need adapter-specific work — expected, not a redo.

## Parked — email and SMS

Simulated outbox/inbox flows on the console over the same transport; nothing above closes the door. Each is a composer, an `outbox-store`, and a console tab when you return to them.

## Cross-cutting

- Persistence: IndexedDB for named databases and their records; in-memory for live interactions; export/import JSON for sharing datasets; one "Reset demo data" per database.
- Demo setup: agent app and console side by side, same browser; phone-as-customer is the only thing that would need the WebSocket transport.
- Provenance on every AI card so stakeholders see records, not invention.
- The sim providers and the profile packs are permanent — demo mode, test harness, and the way new verticals get added.

## Effort and order

Rough effort: Phase 0 about 5–6 days, Phase 1 about 6–8 (schema-driven panels and four full verticals), Phase 2 about 2–3, Phase 3 about 3–4, Phase 4 about 4–5, Phase 5 about 2–3, Phase 6 about 4–5 — roughly six weeks of focused work. Phases 0–4 need no key, no cost, no network; Phases 5 and 6 are the only ones that reach outside the browser (both sides of Phase 6's bot segment are model calls).

Order of attack: Phase 0, then Phase 1 with just the telecom profile (so existing screens keep working while the panels go schema-driven), then Phases 2–4, then the remaining verticals, then Phase 5, then Phase 6. PROMPTS.md lists the steps in this execution order.

- P0.4 — `SimulatedInteractionProvider` lives in `src/adapters/sim/` (not `src/providers/`, which stays types-only per P0.2). **Shape:** the provider is a pure client; an in-window `SimEngine` (the "switch") owns all agent/interaction/transcript state, the state machine and the scripted timers. They talk over a `SimTransport` (`send`/`onMessage`/`close`, fire-and-forget like a socket) — `createBroadcastTransport("agent-sim")` today, a WebSocket transport later via `SimOptions.createTransport`, with the engine moving server-side (`engine: false`). Every method, reads included, is a typed command (`sim-protocol.ts`: `SimCommand` per method, `SimCommandResults`, `SimEvent` derived from `InteractionEvents`, `SimCustomerAction`); the engine sends the reply before the events it caused.
