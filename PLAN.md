# Agent Workspace Simulation — Consolidated Plan

**Target repo:** `~/GitHub-Local/agent-next-gen-demo` (consumes `~/GitHub-Local/lyra-ui` through the Vite source alias; design-system changes land in lyra-ui, app changes land here).

All client-side. The provider layer keeps a real backend (Twilio, CXone ACD) a swap rather than a rewrite; the profile layer keeps a new vertical a data pack rather than a code fork. Step prompts for executing this plan live in PROMPTS.md.

## Phase 0 — Provider architecture and simulation plumbing

1. **Domain model.** App-owned types — `Interaction`, `Message`, `Utterance`, `Entity` (the vertical's primary record: customer/patient/account holder), `RelatedRecord`, `AgentState` — with vendor-agnostic IDs plus an `externalId` slot. Vendor payloads never reach components.
   - **Rich message content** (added 2026-10-16). `Message.content` is a union, not a string: `text`; `html` (email); `media { kind: image | file | audio | video, url, caption?, mime }`; `interactive { prompt, options: [{ id, label }], kind: buttons | list | quickReplies }`. A customer's tap on an option arrives as a reply message carrying `choice: { messageId, optionId }`. `attachments[]` sits alongside. The transcript renders each kind (lyra bubbles for media and interactive); the composer offers only what the channel's capabilities allow (below, Integration readiness).
   - **Channel registry — target, not yet built** (added 2026-10-16; P2.7's first step). Today `channel` is a string enum (voice, chat, email, sms, whatsapp) that runs through the domain, the sim, routing, settings, nav cards and tests; turning it into a registry is a wide refactor, so it waits until social channels (Phase 2 §7) give it a reason. Target shape: `ChannelDef { id, label, kind: voice | chat | email | sms | messaging | social-post, platform?: whatsapp | messenger | instagram | x | tiktok | telegram | wechat | apple-messages | google-business, tempo: sync | async, addressKind: phone | email | handle | platformUserId | postRef, capabilities, icon, messagingWindow?: hours }`. **Tempo is a static property:** voice and chat are sync; every text channel (SMS, WhatsApp, email, social DMs) is async. The built-in five seed the registry; connected platforms add entries; Settings → Channels, the composer, nav rows, Contact History chips and omnichannel routing read it. `Interaction.channel` references a `ChannelDef` id; `Interaction.kind: conversation | social-post`. Until then, social channels exist only as settings placeholders (`channels.social`, P-AIFIRST).
2. **Four provider interfaces** (`src/providers/`, types only). `InteractionProvider` (events: `incoming`, `stateChanged`, `message`, `transcript`, `typing`, `ended`; commands: `accept`, `decline`, `end`, `hold`, `mute`, `transfer`, `sendMessage`, `setTyping`, `dial`, `setAgentState`, `connectAgentLeg`, `disconnectAgentLeg`, `associateEntity`, `setCaseStatus`, `completeWrapUp`, `setRecording`, `setMasked`, `sendDtmf`; reads including `listPresenceOptions` and `listOutboundSkills(channel)`; a `capabilities` map covering hideable UI controls). `MediaProvider` (`unlock`, volume, `audioStateChanged`/`speaking`/`wordBoundary`; no `speak`). `CustomerDataProvider` (`getEntity`, `search`, `findNearMatches`, `create`, `update`, `linkContactMethod`, `getContactHistory`, and a generic `getCollection(name, query)` behind named convenience methods). `AssistProvider` (`suggest`, `extractEntities`, `cancel`; cards and extracted fields arrive as events). All methods async and reject only with `ProviderError` (`not-supported` | `invalid-state` | `not-found` | `network`); all state changes arrive as events.
3. **Provider context.** Supplies the active provider set, the active database handle, and the active `ContactCenterProfile`; chosen by `?provider=sim|twilio|cxone`. UI hides controls a provider's `capabilities` doesn't include.
4. **`SimulatedInteractionProvider`** in `src/adapters/sim/`. A pure client talking over a `SimTransport` (`BroadcastChannel("agent-sim")` today, swappable for WebSocket later) to an in-window `SimEngine` that owns state and scripted timers, with configurable injected latency so the UI is built for a real network from day one. Dev-only `window.__simCustomer` stands in for the customer console until step 6.
5. **Migrate existing simulation behind the provider.** Incremental: new flows first, existing paths after.
   - **5.0 Interaction store + view-model adapter.** A store in `src/provider-context/` that subscribes to the active `InteractionProvider`, hydrates via `getSnapshot()`/`getTranscript()`, upserts snapshot events by id, and exposes hooks (`useAgentState`, `useInteractions`, `useInteraction`, `useTranscript`); plus a pure adapter that groups domain Interactions by `journeyId` into the pages' existing left-nav card view model. Prerequisite for every migration below.
   - **5a Agent leg.** The agent-leg `setTimeout` connect sequence and the in-memory leg-state module move onto `connectAgentLeg`/`disconnectAgentLeg`; also authorizes a backward-compatible lyra `AgentProfile` change (optional controlled leg props).
   - **5b Dial pad / interaction creation** through `dial`. Split in two, because once cards come from the store, every path that creates or changes a card goes through the provider:
     - **5b.1 Provider groundwork** (no page changes): `reopen`, `caseId`/`contactName`/`acceptedAt`, the one-active-voice-contact rule, the engine's demo seed, and the view-model changes (offer exclusion, reopen folding).
     - **5b.2 Pages onto store-backed nav cards**: shared `useNavCards`/`useOutboundDial`, the `journeyId` re-key, notifications/reopen/linking through the provider, and hold/hang-up/dismiss pulled forward from 5d (into a 5b.3 if the plan gets too large).
   - **5d Voice bar, incoming tile and wrap-up onto the provider.** Hold/mute/record/mask/keypad, hang up, Accept/Decline, the session status pill (`setCaseStatus`), and the inline wrap-up card (`completeWrapUp`). Split: **5d.1** provider wiring in shared code (done); **5d.2** (done 2026-10-16): Desk's pieces live in Advanced behind settings (Home tabs from the apps placed as "tab", the omnichannel layout, the New Outbound launcher's tabs and Outbound Calling behaviors), and Desk is deleted (Decisions, P0.5d.2). **5d.3** (next, after P-PROFILES): **layout slots** (`<LayoutSlot anchor=…>`) for the voice bar, the incoming tile and the right panel, so Phase 7's configurable layout is a data change (it starts by checking how much P-SETTINGS' voice-controls location already covers); one `CONTACT_HANDLING_FLAGS` plus capabilities replacing the `SHOW_*` constants; opening a notification expands the nav (row 21); the record-header voice icon (row 11); "Call previous agent" as a Contact History consult placeholder until P0.9.
   - **5c Scenario player; retire page timers** (done 2026-10-15). The engine's scenario player plays the P0.7 scripts; Marcus, Lucas, Tom and Maya are engine contacts on Advanced, and the pages run no scenario timer. Runs after step 7.
6. **Customer console route.** `#/customer-console`, same Vite app, talks only to the sim provider — the agent UI never knows it exists. Replaces `window.__simCustomer`. Handshake: attach to an existing interaction or create one ("Start inbound chat/call as <entity>" or "as unknown caller" with free phone/name entry), carrying identifiers (ANI, email, chat handle) and pre-contact context.
7. **Scenario script format** (runs before 5c). TS/JSON canned lines per entity per channel, expressed as `SimCustomerAction`-compatible steps; loaded from the active profile; Marcus Webb ported as data.
8. **Contract test suite** (pulled forward before the 5.x migrations). `describeInteractionProviderContract(label, factory)` (`src/contract-tests/`), runnable against any `InteractionProvider`: the incoming → accept → message → hold → end → completeWrapUp lifecycle (chat and voice), outbound dial, typing both ways, ack-before-event ordering, idempotent no-op commands, `not-supported`/`invalid-state`/`not-found`, every ended reason through wrap-up, and `dispose()`. Also covers the provider-cache lifecycle. Run with `npm test` (Vitest). **This suite is the bar every adapter must pass.**
9. **Transfer, consult, merge, hand raise and internal messaging** (after 5d.2; added 2026-10-15). The call is the unit of work; the people on it are participants.
   - **9.1 Contract, directory, participants.** Capabilities `transfer.consult`, `conference.merge`, `conference.split`, `assist.monitor`/`whisper`/`barge`. New **`DirectoryProvider`** (`listAgents`, `listQueues`, `listSupervisors`, `getPresence`, `listAddressBooks`; `presenceChanged` events); the sim serves the New Outbound fixtures with presence that changes on its own. **Multiple address books, uploadable:** each is `{ id, name, source: seeded | uploaded | connected, entryCount }` with its entries; the three seeded today (Partner Network, Vendor Directory, Regional Offices) become the sim's, admins upload more as CSV (Settings → Connections → Address books, 9.2), and connected ones come from Outlook/Google (below). The launcher's Address Book group renders however many exist. The New Outbound tabs Agents, Skills and Teams, and the Outbound Calling behaviors Agent, Skill, Address Book and Transfer, go live on this provider. New **`MessagingProvider`** (threads, messages, presence) for agent-to-agent and agent-to-supervisor chat, separate from `InteractionProvider` so internal chats never become customer interactions or Contact History rows. `Interaction.participants[]: { id, role: customer | agent | external, name, state: talking | held | muted, joinedAt }`, changed by events. Merging two customer calls creates one conference interaction and ends the originals with reason `"merged"`; split restores them; a transfer ends with reason `"transferred"` plus the target. Contract suites for both new providers; the interaction suite gains consult/merge/split cases gated on capabilities.
   - **9.2 Flows and UI (shared code, both pages).** Blind transfer (pick a target, hand off, drop). Consult: the customer holds, the target rings, and a consult strip under the voice bar shows "Consulting <name> · mm:ss" with Complete transfer / Merge / Cancel. Merge two existing calls from the held card's chip menu or the bar ("Merge with <other call>"). Agent-to-agent voice is a consult when a call is live and an internal call otherwise; "Call previous agent" becomes a consult action on the history row. **Hand raise:** a button on the voice bar and the chat composer row; raising flags the contact (a hand chip on the nav row) and opens the messaging drawer on a supervisor thread prefilled with the contact context (customer, skill, elapsed, the AI's read of the issue); the supervisor can reply, monitor, whisper, barge or take over, each gated by capability. **Messaging drawer:** a right-side slide-out opened from the top bar, available with or without assignments; tabs per thread (supervisor, teammate, team channel); unread badge on the toggle; a pop-out for a second monitor; it never changes the active assignment. **Nav card:** the title stays the customer; a participant-count badge ("⚇ 3") next to the voice chip, names on hover (try the `statusBadge` slot before adding a lyra prop). **Record header:** an avatar switcher for participants; the selected one drives Customer Profile, Snapshot, Details and AI assist; an agent participant shows a presence card. **Transcript:** one stream labeled by speaker. **Wrap-up card:** one disposition per customer participant, each writing its own Contact History row. Before/afters for all of it.
   - **9.3 Agent console window.** `#/agent-console?as=<agentId>`: a second agent desktop on the same sim session, built on the customer-console plumbing (step 6). Transfer rings there and accepting removes it here; a consult or merge shows the participants in both windows; a hand raise opens there as the supervisor. The Phase 6 virtual agent is listed in the directory as a transfer target (bot-first routing in reverse; it can escalate back).
   - **9.4 Agent-to-agent calls** (added 2026-10-16). Two different things, matching how CXone, Genesys Cloud and Five9 treat them:
     - **Standalone internal call** (an agent dials another agent, no customer involved): an `Interaction` with `channel: "voice"`, `internal: true` and `counterpartAgentId`. It gets its own card and timer. The record header and Contact Details show the *agent* (name, team, skill, presence), not a customer; no case, no customer history tab. Outcome is hidden (capabilities rule); an optional one-field "Internal call reason" (coaching / question / handoff) exists for reporting. `recordInteraction` writes it to the agent's own activity log, never to a customer's Contact History. Launching requires `outbound.calling.agent`; the Agents directory tab is presence-aware (agents who aren't Available are hidden, or the call rings through to the skill's queue). **The internal call's main column is the message thread with the counterpart agent** — the same `MessagingProvider` thread the drawer holds (one source, two views); while that card is selected the drawer collapses that thread to its badge; when the call ends the thread remains in the drawer. The agent card at the top of the main column carries a "Message" affordance.
     - **Consult / transfer on a customer contact:** no new `Interaction`. The second agent joins `participants[]`; the customer is held during the consult; it resolves to transfer (originator drops), conference (both stay) or consult end (second drops). The receiving agent's Contact Details are the customer's, plus a consult banner (who brought them in, their note) that embeds the same messaging thread with the consulting agent. **Wrap-up is per leg:** `wrapUp` is keyed by participant, so the originating agent gets a wrap-up card for their segment on handoff and the receiving agent gets theirs when the contact ends. The customer's Contact History shows one contact with segments ("Jordan → transferred to Sam"), not two contacts. The agent console window shows an incoming consult as an offer on the customer's contact with the pre-contact summary and the consulting agent's note, not as a bare internal call.
     - **Reporting:** internal time is its own bucket, never handle time. Both cases carry `AgentState`-aware controls: an agent on an internal call is off the queue, which is why contact centers gate the feature by role (agents → supervisors/skills; supervisors → anyone) rather than offer it freely.

## Phase 1 — Vertical profiles and database management

1. **`ContactCenterProfile` type and registry.** Each profile declares terminology (entity name and labels), schema (entity fields + related collections with their status vocabularies), generators, scenario scripts, an intent pack (Tier 1 patterns/slots, Tier 2 tools and system prompt), compliance behaviors, dispositions/reason codes, and a handoff-snapshot template.
2. **Verticals.** Build fully: retail/e-commerce (orders, returns, loyalty, payments), collections (debts, payment plans, promises-to-pay, contact attempts), healthcare (appointments, claims, prescriptions, providers), customer service/tech support (tickets, entitlements, devices, known issues). Thinner packs on the same engine: banking (accounts, transactions, cards, disputes), telecom (lines, plans, devices, outages — the current Marcus Webb data lives here), insurance, travel/hospitality, utilities.
3. **Generator engine.** Shared deterministic synthetic-data engine; per-vertical generators with realistic distributions and status mixes (payments mostly succeeded, some declined, occasional refund; claims with denials; tickets across states), plus showcase records guaranteed to make demo questions land — Marcus Webb gets at least five declined payments.
4. **Named databases on IndexedDB (Dexie).** `SimulatedCustomerDataProvider` takes a database handle; create, switch, export/import as JSON, reset to demo. Entities may carry **several `externalId`s** (Salesforce, Zendesk, CXone contact id, …), since the same person exists in more than one connected system.
   - **4a Interaction history persistence** (added 2026-10-15). On `completeWrapUp` the engine writes the finished interaction (participants, duration, outcome, disposition, tags, summary, transcript, end reason) through `CustomerDataProvider.recordInteraction`, emitting `collectionChanged("interactions")`. Home's Contact History, the customer panel's history accordion (7b) and the Details-panel transcript tab for earlier journey contacts read from it; the page-side "Today" row goes away. Reopen pulls the real prior transcript; unknown callers get a provisional record until linked (P4.9). Export/import JSON includes history. Contract test: a completed wrap-up appears in `getContactHistory(entityId)`.
   - **4b Tickets are native** (added 2026-10-15). `tickets` is a related collection on every profile's schema (id, title, status, priority, owner, the contact that opened it, notes). The app creates, updates and closes tickets itself; "Create ticket" from the wrap-up card carries the summary and disposition in. A ticket links to the interaction that opened it and every later contact that touched it, so history rows show the ticket and the ticket shows its contact timeline. The same records are Phase 7 work items (`kind: "ticket"`). A ticketing connection (Zendesk, ServiceNow, Service Cloud) maps the native schema onto the vendor's under the customer-data sync rules; the vendor's id goes in `externalId`.
5. **Create-database wizard.** Pick vertical → name → size and history depth → seed → optional file import → generate → connect.
6. **Vertical-aware import.** `.csv`/`.xlsx` in-browser (PapaParse / SheetJS), column mapping onto the selected profile's schema, preview, validation, dedupe; extra sheets map onto related collections.
7. **Schema-driven panels** — the real work of this phase. Customer Profile card, Details-panel accordions, and the transactions panel become generic entity + related-collections renderers driven by the profile's schema; the current hard-coded layout survives as the telecom profile's rendering.
8. Route `buildCustomerContextOverviewInfo`, contact history, the dial pad, and the console picker through the provider and profile. Marcus Webb becomes a scenario inside the telecom pack rather than a special case.

## Phase 2 — Realtime chat simulation

**Omnichannel layout** (decided 2026-10-15; live since P0.5d.2 behind Settings → Assignments → Omnichannel layout, on in the Phase 2 profile; P2.2 verifies it with a real inbound chat). Channels split by tempo, and **tempo is static** (revised 2026-10-16): **sync** channels (voice, chat) get the main column; **async** channels (email, SMS, WhatsApp, private social DMs) open in the docked right panel from tabs in the record header. WhatsApp is async like SMS, always — the earlier "sync while the customer is actively replying" refinement is dropped; WhatsApp's real differences (rich content, typing and read receipts, the 24-hour window, templates) live in the channel's capabilities, not in layout. **The one thread that moves:** an async thread alone on a card fills the main column; when the agent *accepts* a chat on that card, the chat takes the main column and the async thread goes to the panel in the same frame, panel open, unsent draft preserved — an offered chat never rearranges anything, so the move is always the agent's own action. The main column shows the selected card's conversation: the chat if there is one, otherwise the voice summary content (Autosummary, assist, the wrap-up card at the end). **Voice has no content view**; the voice bar appears under whatever the main column shows whenever the selected card has a call, so chat and call show together. An async thread fills the main column when the card has no sync channel. A slide-out stays open across card switches only if it belongs to the selected card. Unread counts on header tabs; an "awaiting reply" chip on the nav row. **Nav cards are assignment-based**: one card per customer journey, one row per open channel; clicking a row selects the card and activates that channel (chat → main column, voice → bar, async → slide-out); clicking the card header keeps the last active channel; from Home, a row click navigates to the assignment and opens that channel. This supersedes the rows 12/13 deferral. With the setting off, the docked channel preview stays. P-PARKED (email/SMS) renders into the slide-out.

0. **Render performance pass.** Profile which components re-render on a single provider event and why (React Profiler / dev timing hook); smallest fixes (memoized selectors in the store hooks, `React.memo` on heavy subtrees, state splitting). No visual changes; target under ~50ms per event, **measured against a production build** (the slow renders on the dev server are dev-mode overhead; see PROGRESS.md Known gaps).
1. Console chat view: thread (lyra-ui `chat-message`/`conversation-message`), composer, typing toggle, canned lines from the active profile, "End chat."
2. Agent app: `incoming` event for chat creates an inbound interaction via the existing channel-row / interaction-nav flow; messages append; the agent composer calls `sendMessage`; typing both ways.
3. **Unknown-contact state.** No match on the handshake identifier → Profile card shows "New <entity>" with the handle; handoff snapshot says no prior history; an empty "Draft <entity>" card appears in the AI-assist slot, fields from the profile's schema.
4. Handoff snapshot card (former Next Best Action): seeded from pre-contact context through the profile's template; static once the agent takes over.
5. Expose `onCustomerUtterance` / `onAgentUtterance` from the provider's transcript events. Nothing listens yet.
6. **Rich messaging in the sim** (added 2026-10-16; with P2.2 and P-PARKED). The customer console can send media and tap interactive options; the agent composer can send media, buttons/lists and templates on channels whose capabilities allow it. The sim's WhatsApp enforces the 24-hour customer-service window: business-initiated messages outside it may only be approved templates, so the demo shows the real constraint. The sim turns every channel capability on; the per-channel composer hides what a capability says is off.
7. **Social** (added 2026-10-16; P2.7, after P2.2; starts with the channel registry from Phase 0 §1). Two different things:
   - **Private social messaging** — Messenger, Instagram DM, X DM, TikTok DM, Telegram, WeChat, Apple Messages for Business, Google Business Messages — are async messaging channels in the registry, each with its platform's messaging window and template rules, served through `InteractionProvider` by the connected platform's adapter (a CPaaS where it offers them, else CXone Digital / Sprinklr / Khoros / Genesys social). They route like SMS: the panel beside a sync thread, the main column when alone.
   - **Public social** — comments on posts, mentions, reviews (Facebook, Instagram, X, TikTok, Google and app-store reviews) — is interaction kind `social-post`. The card shows the post preview, platform, a public badge and sentiment. Actions: reply publicly; **take private** (spawns a DM thread on the same journey — a channel elevation like "Call now"; the DM opens in the panel beside the post); hide; delete; like; flag for brand/legal. Triage (sentiment, priority, is-this-support) comes from `AssistProvider`; an unmatched author gets a provisional entity until linked (P4.9). A Home queue section "Social" with per-platform tiles. **Routing:** a social-post is main-column content — a thing the agent works on, not a thread they're in. Wrap-up and Outcome apply like any contact; public replies log to Contact History with a link to the post. The sim seeds a few posts and comments and plays the take-private handoff.
   - **Settings:** Channels lists registry entries grouped by platform (until P2.7, `channels.social` placeholders from P-AIFIRST); Connections gains a "Social" seam row (platform, pages/accounts, which channels it provides). **Integration readiness:** contract cases for social-post (reply publicly, take-private spawning a thread, hide/flag as capabilities); a SOCIAL adapter joins the P-ADAPTER order after CXone.

## Phase 3 — Voice call simulation

1. **`SimulatedMediaProvider`.** `MediaProvider` has no `speak()`: the sim media provider subscribes to transcript events itself and drives TTS from them. TTS via `speechSynthesis` with a voice per persona; optional agent-side `SpeechRecognition` (Chrome) while unmuted, with typed agent lines on the console as fallback.
2. Console voice view: composer, canned lines, voice/rate/pitch, "Hang up."
3. Inbound ringing via the provider's `incoming` event drives the existing incoming-call UI; Answer is the audio-unlock gesture.
4. Playback: `transcript` events append to the transcript and queue TTS (no overlap); audio stops when the interaction's state leaves `active`/`held` (the move to wrap-up or ended), not on `ended`, which can fire long after the call dropped; pause/resume on `hold`.
5. Realism: `onboundary` reveals words in sync with audio; `onstart`/`onend` drive the "customer speaking" indicator in the voice call controls.
6. Same unknown-contact state as chat; speech normalizers for emails ("dot"/"at") and spelled-out names.

## Phase 4 — AI assist, Tier 1: deterministic and grounded

1. **`SimulatedAssistProvider`, router half.** Loads the active profile's intent pack: `{ patterns, slotExtractor, collection, query, card }`; runs on every utterance and on agent-initiated asks.
2. **Generic parameterized handlers.** One engine — `getCollection(name, { status?, limit?, sort?, since?, until?, minAmount? })` — with filter/sort executed in code; vocabulary comes from the profile, so "last 5 declined payments" and "last 3 denied claims" are the same code path.
3. **Slot extraction.** Counts, the profile's status vocabulary, recency, date phrases, amounts. "Show me the last 5 declined payments" → `{ status: "declined", limit: 5, sort: "newest" }`. Unfilled slots defer to Tier 2 rather than guess.
4. **Cards render records, not prose.** Cards arrive as `AssistProvider` `card` events (successive full snapshots). Title restates the interpreted query; body is the actual table; a provenance line names the collection.
   - **4a Card-type registry and configurable placement** (added 2026-10-15). Card types (account overview, interstitial, records, text, hint, and new lyra types as they're built) are a registry: a lyra component plus a typed content schema. `AssistCard` gains `type` and `content` shaped by that schema; the provider emits data and the registry picks the renderer, so new lyra types register without page edits. **Lyra rule:** components take a typed `content` object, do no fetching or AI calls, and bubble actions up (`onAction(actionId)`). **Templates per client** (profile config): which fields each type shows, in what order, with what labels, referencing the profile's schema (a retail account overview shows orders and loyalty; healthcare shows coverage and appointments). **Placement:** `pinned` (lives in a Contact Details tab or accordion) or `auto` (appears in the main column's assist slot on a trigger: contact start, intent match, Tier 1 hit, escalation handoff, wrap-up); auto cards can be dismissed. **Interstitials** are auto cards that hold the assist slot until acknowledged (verify identity, compliance reminder), which is how 4.5's gates render. Configured on Settings per profile with preview-as-agent.
5. **Compliance gates in front of cards.** Added to the `AssistCard` contract in this step (deliberately left out of P0.2). Healthcare: nothing PHI-bearing renders until the agent marks identity verified ("Verify identity to view"). Collections: right-party verification and a mini-Miranda reminder card at call start, promise-to-pay capture. Banking: card numbers masked, tying into the existing Mask control.
6. **Placement per channel.** Voice — inline overlay in the main contact container, expands in place. Chat — composer-adjacent suggestion strip, never interleaved into the thread. Expanded state reuses the Details-panel Accordion/card treatment.
7. **Actions map to the app.** "View full history" opens the related-records panel; "Open case/ticket/claim" jumps to it.
8. **Agent ask box** on lyra-ui `ai-input`/`ai-panel`/`ai-process`; same router, same cards.
9. **Progressive entity creation, deterministic half.** Regex extractors for email, phone, ZIP, account/member number, amounts, name heuristics; detected values arrive as `AssistProvider` extracted events and fill the Draft card live, each tagged with its source utterance. Before save, `findNearMatches` offers "Link to <existing>?" vs "Create new." Agent saves with one click or edits; the AI never writes silently. Interaction ended without saving → auto-save flagged *provisional*. On save, the interaction re-associates and Profile/Snapshot/history/table update live; expanded state reuses the existing create form, fields from the profile's schema.
10. No-match fallback: nothing (voice) or a quiet "I can look up <collections>…" hint (chat), listing what the profile actually has.
11. **Knowledge base, Tier 1** (added 2026-10-15). `knowledge` is a profile-level collection (articles: title, body, tags, product/skill scope, source, last updated), imported from Markdown/HTML/PDF/CSV through the wizard's import path, or synced from a vendor KB (Zendesk Guide, Salesforce Knowledge, Confluence, SharePoint) through a `KnowledgeProvider` seam under the customer-data sync rules. The router retrieves by tag and keyword and surfaces matches as a `records` card with provenance (title, last updated); the agent opens an article in the Details panel or the draggable panel. Which sources are active per skill, and whether the AI may quote or only link, are Settings.
   - **11a Quick replies** (added 2026-10-16). A native quick-reply library — `{ id, title, body, channels, skills, tags, source: "native" | <vendor>, externalId?, sourceBody? }` — managed in Settings → Knowledge and served by `KnowledgeProvider.listQuickReplies(skill, channel)`. `AssistProvider` ranks and fills them for the current contact; the composer's suggestion chips on chat/SMS/email/WhatsApp draw from the library first and AI-drafted replies second; an AI draft can be "saved as quick reply". **Vendor libraries are sync sources, not replacements:** CXone Quick Replies, Genesys canned responses, Zendesk macros and Salesforce Quick Text map onto the native schema through a connection under the customer-data sync rules — read-only by default (the library is managed in the vendor), two-way when configured — so the agent sees one library whichever system each entry came from.
     - **Variable syntax across vendors.** (1) One canonical form in our data — `{customer.firstName}`, `{agent.name}`, `{case.id}` — against an app-owned variable catalog; vendor syntax never lives in our records. (2) Translation at the adapter edge: each adapter carries a `variableMap` and a tokenizer for its delimiters (CXone `{{FirstName}}`, Zendesk `{{ticket.requester.first_name}}`). On import, an unmapped token becomes `{unknown:<original>}` and the entry is flagged in Settings ("1 variable not recognized"), never silently dropped; on write-back, a canonical variable with no vendor equivalent refuses the write for that entry with the reason; `sourceBody` keeps the vendor's original for a lossless round trip. (3) Render-time safety: every variable resolves against the live contact; one that can't (no first name on an unknown caller) becomes a highlighted placeholder the agent must fill or delete before Send is enabled — for AI-filled replies too.
     - **Formatting:** email replies are HTML; SMS, chat and WhatsApp are plain text. The adapter normalizes per channel on import and the composer strips markup on plain channels.
     - **Vendor-only features** (CXone attachments on a reply, Zendesk macro *actions* such as set-status) don't map to a text reply: the text imports, the rest is recorded as `unsupported` on the entry, and P-MAPPINGS' dry-run preview shows what will and won't sync before anyone syncs.
     - **Templates are the same library** (added 2026-10-16). The quick-reply library generalizes to a templates library: `kind: quickReply | template`; `format: text | html | whatsapp-template`; `channels`; `variables`; `approval: { status: draft | pending | approved | rejected, vendorId? }`. WhatsApp business-initiated messages outside the 24-hour window require an *approved* template (Meta's program, via the CPaaS), so the composer's "Insert template" offers only approved ones there. Sync sources by kind: CXone for quick replies, **Mailchimp** (and the profile's own HTML templates) for email templates, WhatsApp Business via the CPaaS for approved message templates — all through the same `variableMap` / `sourceBody` / `unsupported` machinery. One library, filtered by channel, kind and approval, feeds both the chips and "Insert template".

## Phase 5 — AI assist, Tier 2: a real model with tools

1. **Model access** inside `AssistProvider`: a ~30-line proxy holding the key, direct browser calls behind Anthropic's explicit opt-in header (localhost only), or a local model via Ollama.
2. **Tools and persona from the profile.** The generic collection query exposed with the profile's schemas; `propose_entity_fields` for conversational addresses, employers, contact preferences, reason-for-contact — feeding the Draft card with the same confirm-before-save rule. System prompt carries the vertical's persona and compliance rules.
3. **Hybrid rule.** Retrieval stays on the Tier 1 router; the model does synthesis only — "summarize why she's frustrated," "draft a reply offering the credit," "what next" — with Tier 1 results as context, never answering a data question from its own head.
4. **Streaming** into cards; **conversation context** (last N utterances + handoff snapshot) per request.
5. Replace Phase 4's no-match fallback with a Tier 2 call.
6. **Knowledge base, Tier 2** (added 2026-10-15). Articles are chunked and embedded (in-browser model or the proxy); the model answers with citations to the chunks it used, never from its own head (the hybrid rule). Guided flows: an article can carry steps, and the assist card walks the agent through them as a checklist that follows the conversation.
7. **Setup assistant** (added 2026-10-15; the templates half ships with P1.1/P1.2, the conversational half here). Each vertical profile ships a complete configuration bundle: layout preset, Contact Details tabs and fields, AI card templates and placements, dispositions, compliance gates, KB sources, suggested connections. The assistant asks a few questions (kind of contact center, channels, systems in use, what agents handle most, compliance regime) and proposes a configuration diff over the nearest template, shown item by item for accept/edit/reject; nothing applies without review. It only emits configuration in the same typed schema the hand editors use, can't remove compliance gates, and every applied change is versioned with rollback. Auto-tune from reporting events comes with Phase 7.

## Phase 6 — Virtual agent and escalation to a human

A bot handles the contact first; the customer gets irate or asks for something beyond the bot's authority; the bot escalates, and the human agent takes it over in the app with the whole history in front of them. Both sides of the bot segment are model-driven — no scenario script plays either the customer or the bot (P0.7 scripts remain the console's manual canned-lines panel only). Depends on chat (Phase 2), voice (Phase 3), the handoff snapshot (P2.4), the console (P0.6) and model access (P5.1), so it runs after Phase 5.

1. **Domain and contract.** `Interaction.origin` gains `"escalated"`. `Interaction.escalation?: { at, reason: "customer-requested" | "out-of-authority" | "sentiment" | "bot-uncertain", summary, intent, sentimentTrend, botAttempts[], pendingRequest? }` is written by whoever ran the bot segment and is the only thing the human-side UI consumes. `Message`/`Utterance` get `author: "customer" | "agent" | "bot"` (today's two plus bot); the bot segment is the same Interaction's transcript up to `escalation.at` — same `InteractionId`, same `journeyId`, no second contact. New **`BotAgentProvider`** contract in `src/providers/` (types only): `handle(interactionId)`, `onCustomerTurn(turn)`, `release(interactionId)`; events `botTurn`, `thinking`, `escalate`, `released`; `ProviderError` only; `capabilities` for channels and `canEscalate`. The bot converses and *asks* to escalate; routing stays with the engine (or a real ACD). `ContactCenterProfile` gains a **bot pack**: persona, authority (what the bot may approve, with limits), escalation policy (which triggers apply and their thresholds), and the bot's tools over `getCollection`. Contract tests: `describeInteractionProviderContract` gains "an escalated `incoming` carries `escalation` and `getTranscript` returns the bot segment", gated on a new `InteractionProvider` capability `escalation` so an adapter with no virtual agent skips it per the going-real rule; new `describeBotAgentProviderContract` (turn ordering, escalate fires at most once, `release` cancels in-flight work, `not-supported` gating).
2. **Simulated bot.** `SimulatedBotAgentProvider` in `src/adapters/sim/` on the P5.1 model backends (backend selection lifted into a shared module if it still lives inside the assist adapter). System prompt = the profile's persona, authority and compliance rules; tools = the profile's collection query plus `escalate(reason, summary)`. **Bot-first routing** in `SimEngine`: a console-started contact flagged bot-first is handed to the bot; `escalate` moves it to the queue and the agent app receives `incoming` with `escalation` populated and the bot transcript already in place. The engine honors an explicit "I want a person" even if the model misses it (policy guard, not a script). Chat first.
3. **Console AI-customer mode.** Beside typed and canned lines, "Play as <entity>": a model-driven persona built from the entity record and contact history plus a goal and temperament chosen on the console (refund over the bot's limit, rising frustration, …). It emits ordinary `SimCustomerAction` messages, so the engine can't tell it from a typed customer. During the bot segment the console voices both parties with its own TTS — no agent is on the contact yet.
4. **Agent-side handoff.** Incoming tile shows "Escalated from virtual agent" with the reason; accepting loads the transcript with bot turns rendered distinctly and a handoff divider at `escalation.at` (lyra transcript edit authorized); the handoff snapshot (P2.4) is seeded from `escalation` through the profile's template, then frozen; AI assist resumes over the full transcript. Built once in the shared contact-handling code and consumed by both pages (parity decision). Accept drops the whole bot segment into the transcript at once — a browser check against P2.0's budget.
5. **Voice.** Same path on voice: the bot segment is voiced on the console; on Answer the console stops the bot's voice and `SimulatedMediaProvider` takes over the customer's voice mid-call on the same Interaction, with no re-ring.

## Phase 7 — Work items, schedule, apps and configuration

Added 2026-10-15. Assignments grow beyond customer contacts to every unit of work an agent owns, and the app's layout, panels and content become client-configurable data. Depends on P1.4 and P1.4a; 7.3 can run earlier for demos.

1. **`WorkItem` and `WorkProvider`.** `WorkItem { kind: contact | ticket | coaching | meeting | task }`; a journey is the contact kind. Views: ticket detail with notes; coaching session with the recorded interaction, transcript and scorecard; meeting agenda; task checklist. Before/afters.

There's no separate calendar view (the `home.calendarView` flag was retired in P0.5d.2). `CalendarProvider` seam for WFM schedules and Outlook/Google.

Each app declares an id, name, icon, URL template and accepted contexts (customer record, case, ticket, interaction). Real adapters: Salesforce Lightning Out / Canvas, ServiceNow embedded pages, Zendesk apps; auth inside the adapter. Demo: a sim CRM app in this repo (`#/sim-app/crm`) that renders a fake record for the given customer and posts "record saved" back, updating the Snapshot live; a second placeholder app with an unreachable URL shows the error and reload state. 7. **Configurable layout.** A `LayoutConfig` type: which regions exist (left nav, record header, main column, right panel, bottom bar), what each holds (nav entries, header tabs, panels, apps), and where the voice bar is anchored (bottom, under the header, docked right). Phase 1 and Phase 2 are built-in workspace profiles (P0.5d.2, P-PROFILES); the page renders through the layout slots 5d.3 introduces. A user's edits are a diff over the applied profile, in the settings store; Reset drops it. Configurable: side nav (show/hide, collapsed, entries, order), header tabs and panels (which, order, docked vs floating), which apps show, the voice bar anchor. **Never configurable:** contact-handling behavior, capability gating, hold/wrap-up rules, dialing. Edited on Settings through toggles and reorder lists, not free drag, with live preview; a `locked` flag per region for admin-served presets.
8. **Setup assistant, auto-tune half** (the templates and the conversational half are 5.7). Reads 7.5's events and proposes changes ("agents open the orders accordion on 80% of calls; pin it"), same review flow.

## Customer data: the app is the source of truth

Added 2026-10-15. The app's database is the system of record for the agent's work; CRMs, ticketing systems and KBs are feeds and sinks.

- **The AI reads only `CustomerDataProvider`**, never a CRM adapter, so it always sees the latest notes, Draft saves, outcomes and history (1.4a), even when sync is behind or the connection is down.
- **Sync modes per connection:** `manual` (file import, 1.6), `interval` (poll every N minutes), `realtime` (webhooks or a vendor event stream through the relay). A CRM adapter per source (Salesforce, Zendesk, HubSpot, Dynamics) maps vendor records onto the profile's schema with the same column mapping as 1.6, saved as a reusable mapping; related collections (orders, tickets, cases) map the same way. `entityChanged`/`collectionChanged` refresh Profile and Snapshot live mid-contact. The sim gets a "simulate sync" control that mutates records on an interval, and a "simulate conflict" control.
- **Write-back:** local edits queue through the adapter when the connection allows; a record with pending writes shows a "pending sync" chip. Writes are idempotent (client-generated change id) and retried; a rejected write (vendor validation) stays queued with its error shown on the record.
- **Conflict handling:** per-field `authority: app | crm | newest` in the profile schema (contact facts default to `newest`; notes and dispositions to `app`), with the losing value kept in a conflict note on the record. Timestamps are the vendor's `lastModified` and the proxy's clock, never the browser's. Never delete locally on sync: a record deleted or merged in the CRM is marked "archived in CRM" and keeps working; merges map through `externalId`. Unknown vendor fields are kept raw under the record and listed as unmapped in the mapping screen; sync never fails outright. A "Sync" section on Settings lists conflicts, pending and failed writes with resolve/retry.
- **Provenance per field:** where it last came from (agent, CRM import, AI extraction) and when, shown on cards ("updated by you 2 min ago" / "from Salesforce 1h ago"); P4's provenance line reuses it.
- **Offline:** the app works with every connection down; sync catches up later.
- Contract tests: an agent edit is visible to `suggest()` before any sync; an import doesn't overwrite a newer local edit; write-back queues and drains; same-field conflict by authority; delete-while-open; rejected write retry; unknown field preserved.

## Integration readiness — how we know the seams will hold

Added 2026-10-15. The pages never test against a vendor; they test against the contract, and the contract is what every vendor adapter has to satisfy.

- **One contract suite per seam, and a real adapter is done only when it passes it:** `InteractionProvider` (P0.8), `CustomerDataProvider` (P1.4), `BotAgentProvider` (P6.1), `DirectoryProvider` and `MessagingProvider` (P0.9), `KnowledgeProvider` (P4.11), `WorkProvider`, `AppProvider`, `ReportingSink` (Phase 7). An adapter may skip a test only where its own `capabilities` say the feature is off.
- **Contracts are shaped from the vendors, not from the sim.** Before each seam's contract is final, a mapping checklist against the real APIs (CXone Agent API events, Twilio TaskRouter/Conversations, Genesys Platform API, Zendesk tickets, Mailchimp campaigns, a WFM schedule export, Salesforce/Zendesk records) records how each method and event maps and what doesn't; what doesn't map becomes a capability flag.
- **One small backend:** a proxy/relay service holding vendor keys, exchanging tokens, and receiving webhooks as a websocket relay (the reason `SimTransport` swaps for a websocket). P5.1's model proxy is the same service. The browser never holds a secret.
- **The relay is a real deliverable, not glue** (added 2026-10-16). Vendors push events by webhook — an HTTP POST to a URL we own when a call arrives, an SMS lands, a call ends, a recording is ready — and a browser tab can't receive one, so the relay is the only place a real integration can start. It owns four jobs, each vendor-agnostic in the same way the adapters are:
  - **Webhook receiver:** public URLs per connection, signature verification (Twilio `X-Twilio-Signature`, Zendesk/Salesforce HMACs), idempotency on the vendor's event id, and a dead-letter log for anything it can't parse.
  - **Routing decisions for voice:** for Twilio the webhook *response* is the instruction (TwiML: connect to this agent's browser client, hold, queue, transfer), so the engine's routing rules (skill, presence, channels, one call per customer, auto-hold) run in the relay for real, not in the browser. CXone keeps routing on its side; the relay only forwards.
  - **Fan-out to agent sessions** over the WebSocket `SimTransport` becomes; each vendor payload is translated by the adapter into our domain events (`incoming`, `message`, `stateChanged`, `ended`, `collectionChanged`) before it reaches a browser. Nothing in the UI changes.
  - **Outbound webhooks:** Data Memorialization (P-MAPPINGS) is the relay writing to the connected system or firing a configured URL on a trigger; inbound CRM webhooks (a ticket updated elsewhere) become `collectionChanged` under the customer-data sync rules.
  - Built in P-ADAPTER's first step (Twilio) and reused by every later adapter; record-and-replay captures its webhook payloads as fixtures so the suites run without a vendor.
- **Carriers are not a seam** (added 2026-10-16). One CPaaS account (Twilio, Vonage, Telnyx, Bandwidth) carries voice and SMS on the same numbers, so a customer connects one platform and both channels work; carrier choice, BYOC/SIP trunks and number inventory live inside the adapter. A second connection appears only when the customer connects a second *platform* (CXone for voice, a CPaaS for SMS/WhatsApp), never to model a second carrier. Channel onboarding is per channel regardless of carrier (US SMS: 10DLC or toll-free verification; WhatsApp: Meta's business program). Settings → Connections shows "Phone system: Twilio (voice + SMS)" as one row with its numbers under it.
- **Per-channel capabilities** (added 2026-10-16). Rich messaging differs by channel and by number, so the provider's `capabilities` map gains a per-channel block the composer reads: `channels.sms.media` (MMS), `channels.whatsapp.interactive`, `channels.whatsapp.templates`, `channels.rcs.richCards`, `channels.email.html`, `channels.*.attachments`. The CPaaS reports these per number; the adapter fills them; the sim sets them all on. Hide, don't disable: a composer control for a capability that's off doesn't render.
- **Identity:** several `externalId`s per entity, so one customer maps across systems.
- **Record and replay:** when a real adapter runs, capture vendor events as JSON fixtures and replay them in tests, so the suites cover real payloads and the real integration can be demoed offline.
- **Connector mappings and data memorialization** (P-MAPPINGS, before P-ADAPTER; Zendesk needs it). Each Connection in Settings gets two sub-tabs:
  - **Connector Mappings:** for each of our entities (customer, ticket, account, interaction, quick reply — P4.11a), a field-by-field map to the connected system's object and fields, with a direction (lookup / write / both) and a per-field authority (app wins / system wins / newest wins; the authority model from "Customer data" above), plus the search keys used for identification and screen pop.
  - **Data Memorialization:** named mappings (name, description, entity type, field set) that run on a trigger (contact accepted, outcome saved, wrap-up complete, transfer) and write interaction data (disposition, notes, duration, transcript link, agent, skill) to the connected system. Several per connection, with a dry-run preview.
  - Stored in the settings store under `connections.<seam>.mappings`; the sim adapter logs what it would have written.
- **Prove the pattern early, in order:** Twilio (free trial, well documented, real calls) → Zendesk (free sandbox, plain REST, tickets) → CXone (the one that matters; needs a tenant and Agent API credentials) → a WFM adapter → an AI-agent vendor. Each is a P-ADAPTER step with its own suite run.

### Going real later — what each seam swaps to

`InteractionProvider` → CXone Agent API event stream + actions, or Twilio TaskRouter + Voice/Conversations. `MediaProvider` → CXone integrated softphone or Twilio Voice SDK. `CustomerDataProvider` → a CRM or your own API, with the profile's schema as the mapping target — AI grounding and schema-driven panels come along for free. `AssistProvider` → a server-side service or vendor copilot. `BotAgentProvider` → a hosted conversational agent (ElevenLabs Conversational AI, Vapi, Retell, OpenAI Realtime) behind a thin adapter — or nothing at all when the ACD's own virtual agent (CXone Virtual Agent Hub, Twilio Studio) runs the bot segment server-side, in which case the only requirement is that the `InteractionProvider` adapter populates `escalation` and the bot-authored transcript on `incoming`. Auth, tokens, and webhooks live inside the adapter; the browser-side contract doesn't change. An adapter counts as done only when it supplies an `InteractionContractHarness` (its provider, plus a `customer` driver backed by a fake vendor backend) and passes `describeInteractionProviderContract` under `npm test`; it may skip a test only where its own `capabilities` say the feature is off. Transfer/consult semantics, ACW/disposition, and WebRTC setup will need adapter-specific work — expected, not a redo.

`DirectoryProvider`/`MessagingProvider` → CXone Agent API (agents, teams, skills, presence; internal chat), Genesys Users/Queues and agent chat, Salesforce Omni-Channel presence, or Teams/Slack for messaging. `WorkProvider`/`CalendarProvider` → Salesforce/ServiceNow tickets, NICE/Verint/Calabrio WFM schedules, Outlook/Google calendars. `AppProvider` → Salesforce Lightning Out / Canvas, ServiceNow, Zendesk apps. `KnowledgeProvider` → Zendesk Guide, Salesforce Knowledge, Confluence, SharePoint. `ReportingSink` → CXone Reporting, Genesys analytics, a warehouse.
