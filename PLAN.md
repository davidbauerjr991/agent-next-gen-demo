# Agent Workspace Simulation — Consolidated Plan

**Target repo:** `~/GitHub-Local/agent-next-gen-demo` (consumes `~/GitHub-Local/lyra-ui` through the Vite source alias; design-system changes land in lyra-ui, app changes land here).

All client-side. The provider layer keeps a real backend (Twilio, CXone ACD) a swap rather than a rewrite; the profile layer keeps a new vertical a data pack rather than a code fork. Step prompts for executing this plan live in PROMPTS.md.

## Phase 0 — Provider architecture and simulation plumbing

1. **Domain model.** App-owned types — `Interaction`, `Message`, `Utterance`, `Entity` (the vertical's primary record: customer/patient/account holder), `RelatedRecord`, `AgentState` — with vendor-agnostic IDs plus an `externalId` slot. Vendor payloads never reach components.
   - **Rich message content** (added 2026-10-16). `Message.content` is a union, not a string: `text`; `html` (email); `media { kind: image | file | audio | video, url, caption?, mime }`; `interactive { prompt, options: [{ id, label }], kind: buttons | list | quickReplies }`. A customer's tap on an option arrives as a reply message carrying `choice: { messageId, optionId }`. `attachments[]` sits alongside. The transcript renders each kind (lyra bubbles for media and interactive); the composer offers only what the channel's capabilities allow (below, Integration readiness).
   - **Channel registry — target, not yet built** (added 2026-10-16; P2.7's first step). Today `channel` is a string enum (voice, chat, email, sms, whatsapp) that runs through the domain, the sim, routing, settings, nav cards and tests; turning it into a registry is a wide refactor, so it waits until social channels (Phase 2 §7) give it a reason. Target shape: `ChannelDef { id, label, kind: voice | chat | email | sms | messaging | social-post, platform?: whatsapp | messenger | instagram | x | tiktok | telegram | wechat | apple-messages | google-business, tempo: sync | async, addressKind: phone | email | handle | platformUserId | postRef, capabilities, icon, messagingWindow?: hours }`. **Tempo is a static property:** voice and chat are sync; every text channel (SMS, WhatsApp, email, social DMs) is async. The built-in five seed the registry; connected platforms add entries; Settings → Channels, the composer, nav rows, Contact History chips and omnichannel routing read it. `Interaction.channel` references a `ChannelDef` id; `Interaction.kind: conversation | social-post`. Until then, social channels exist only as settings placeholders (`channels.social`, P-AIFIRST).
- **The assignment is the unit of work; the interaction is a leg (added 2026-10-23).** An **Assignment** is what the agent is handed and what gets outcomed: one customer, one status, one disposition, tags, summary, the NBA queue, the Real-Time Summary and the reference column are all per assignment (`assignmentId`; `externalId` carries the vendor's case/contact/conversation id). An assignment has **parts** of two kinds: **legs** — one `Interaction` per channel session (voice, chat, email, SMS, WhatsApp, social DM), owning start/end, duration, hold, recording, transfer, address and after-call work (the vendor's clock) — and **work items** (Phase 7's `WorkItem`: callback in P0.9, payment, ticket update, approval, flow run, scheduled follow-up), owning kind, status, due/scheduled time and result. Messages and utterances key to the leg. The nav card is the assignment with one row per leg and per work item. Several issues in one conversation are one assignment with several **tickets** (1.4b); the Outcome carries one primary disposition plus a resolution line per ticket. A customer returning later is a new assignment, linked through the Journey Summary and open tickets. `journeyId`/`caseId` as the grouping key are retired in favour of `assignmentId` (P0.9 re-key); `caseId` remains the external case reference. The hierarchy and the vendor mapping are in docs/assignment-terminology-map.pdf. **Two rules that never vary:** after-call work runs per leg, on the leg's end; the outcome is due when the last leg closes or the agent closes the assignment early. **Assignment kinds are a registry (added 2026-10-24).** `conversation`, `callback`, `meeting`, `training`, `task` (ticket work), `campaign-block`, and later `coaching` and `evaluation` (P-QM). Each kind declares its nav-card row, its main-column cells (through the canvas registry: a meeting's action area is agenda, notes and join; a training's is the module; a callback's is the dial card and the customer's stream; a task's is the ticket and its actions), and its **outcome shape** (a disposition for conversations and callbacks; notes + action items for a meeting; completion + score for training; ticket status for a task; a scorecard for an evaluation). Legs can join any kind (a task gains a voice leg when the agent calls the customer). Kinds arrive from providers: InteractionProvider (conversations), P0.9's WorkItem (callbacks), the WFM/schedule and calendar connections (meetings, training), CampaignProvider (blocks), QM (coaching, evaluations). **Role presets** (P-EMPLOYEES) decide which kinds a person sees: agents — conversations, callbacks, meetings, training, tasks; supervisors — coaching, evaluations, team meetings, escalations; sales — callbacks, campaign blocks, follow-ups.
2. **Four provider interfaces** (`src/providers/`, types only). `InteractionProvider` (events: `incoming`, `stateChanged`, `message`, `transcript`, `typing`, `ended`; commands: `accept`, `decline`, `end`, `hold`, `mute`, `transfer`, `sendMessage`, `setTyping`, `dial`, `setAgentState`, `connectAgentLeg`, `disconnectAgentLeg`, `associateEntity`, `setCaseStatus`, `completeWrapUp`, `setRecording`, `setMasked`, `sendDtmf`; reads including `listPresenceOptions` and `listOutboundSkills(channel)`; a `capabilities` map covering hideable UI controls). `MediaProvider` (`unlock`, volume, `audioStateChanged`/`speaking`/`wordBoundary`; no `speak`). `CustomerDataProvider` (`getEntity`, `search`, `findNearMatches`, `create`, `update`, `linkContactMethod`, `getContactHistory`, and a generic `getCollection(name, query)` behind named convenience methods). `AssistProvider` (`suggest`, `extractEntities`, `cancel`; cards and extracted fields arrive as events). All methods async and reject only with `ProviderError` (`not-supported` | `invalid-state` | `not-found` | `network`); all state changes arrive as events.
3. **Provider context.** Supplies the active provider set, the active database handle, and the active `ContactCenterProfile`; chosen by `?provider=sim|twilio|cxone`. UI hides controls a provider's `capabilities` doesn't include.
4. **`SimulatedInteractionProvider`** in `src/adapters/sim/`. A pure client talking over a `SimTransport` (`BroadcastChannel("agent-sim")` today, swappable for WebSocket later) to an in-window `SimEngine` that owns state and scripted timers, with configurable injected latency so the UI is built for a real network from day one. Dev-only `window.__simCustomer` stands in for the customer console until step 6.

Handshake: attach to an existing interaction or create one ("Start inbound chat/call as <entity>" or "as unknown caller" with free phone/name entry), carrying identifiers (ANI, email, chat handle) and pre-contact context.

9. **Transfer, consult, merge, hand raise and internal messaging** (after 5d.2; added 2026-10-15). The call is the unit of work; the people on it are participants.
   - **9.1 Contract, directory, participants.** Capabilities `transfer.consult`, `conference.merge`, `conference.split`, `assist.monitor`/`whisper`/`barge`. New **`DirectoryProvider`** (`listAgents`, `listQueues`, `listSupervisors`, `getPresence`, `listAddressBooks`; `presenceChanged` events); the sim serves the New Outbound fixtures with presence that changes on its own. **Multiple address books, uploadable:** each is `{ id, name, source: seeded | uploaded | connected, entryCount }` with its entries; the three seeded today (Partner Network, Vendor Directory, Regional Offices) become the sim's, admins upload more as CSV (Settings → Connections → Address books, 9.2), and connected ones come from Outlook/Google (below). The launcher's Address Book group renders however many exist. New **`MessagingProvider`** (threads, messages, presence) for agent-to-agent and agent-to-supervisor chat, separate from `InteractionProvider` so internal chats never become customer interactions or Contact History rows. `Interaction.participants[]: { id, role: customer | agent | external, name, state: talking | held | muted, joinedAt }`, changed by events. Merging two customer calls creates one conference interaction and ends the originals with reason `"merged"`; split restores them; a transfer ends with reason `"transferred"` plus the target. Contract suites for both new providers; the interaction suite gains consult/merge/split cases gated on capabilities.
   - **9.2 Flows and UI (shared code, both pages).** Blind transfer (pick a target, hand off, drop). Consult: the customer holds, the target rings, and a consult strip under the voice bar shows "Consulting <name> · mm:ss" with Complete transfer / Merge / Cancel. Merge two existing calls from the held card's chip menu or the bar ("Merge with <other call>"). Agent-to-agent voice is a consult when a call is live and an internal call otherwise; "Call previous agent" becomes a consult action on the history row. **Hand raise:** a button on the voice bar and the chat composer row; raising flags the contact (a hand chip on the nav row) and opens the messaging drawer on a supervisor thread prefilled with the contact context (customer, skill, elapsed, the AI's read of the issue); the supervisor can reply, monitor, whisper, barge or take over, each gated by capability. **Messaging drawer:** a right-side slide-out opened from the top bar, available with or without assignments; tabs per thread (supervisor, teammate, team channel); unread badge on the toggle; a pop-out for a second monitor; it never changes the active assignment. **Nav card:** the title stays the customer; a participant-count badge ("⚇ 3") next to the voice chip, names on hover (try the `statusBadge` slot before adding a lyra prop). **Record header:** an avatar switcher for participants; the selected one drives Customer Profile, Snapshot, Details and AI assist; an agent participant shows a presence card. **Transcript:** one stream labeled by speaker. **Wrap-up card:** one disposition per customer participant, each writing its own Contact History row. Before/afters for all of it.
   - **9.3 Agent console window.** `#/agent-console?as=<agentId>`: a second agent desktop on the same sim session, built on the customer-console plumbing (step 6). Transfer rings there and accepting removes it here; a consult or merge shows the participants in both windows; a hand raise opens there as the supervisor. The Phase 6 virtual agent is listed in the directory as a transfer target (bot-first routing in reverse; it can escalate back).
   - **9.4 Agent-to-agent calls** (added 2026-10-16). Two different things, matching how CXone, Genesys Cloud and Five9 treat them:
     - **Standalone internal call** (an agent dials another agent, no customer involved): an `Interaction` with `channel: "voice"`, `internal: true` and `counterpartAgentId`. It gets its own card and timer. The record header and Contact Details show the *agent* (name, team, skill, presence), not a customer; no case, no customer history tab. Outcome is hidden (capabilities rule); an optional one-field "Internal call reason" (coaching / question / handoff) exists for reporting. `recordInteraction` writes it to the agent's own activity log, never to a customer's Contact History. Launching requires `outbound.calling.agent`; the Agents directory tab is presence-aware (agents who aren't Available are hidden, or the call rings through to the skill's queue). **The internal call's main column is the message thread with the counterpart agent** — the same `MessagingProvider` thread the drawer holds (one source, two views); while that card is selected the drawer collapses that thread to its badge; when the call ends the thread remains in the drawer. The agent card at the top of the main column carries a "Message" affordance.
     - **Consult / transfer on a customer contact:** no new `Interaction`. The second agent joins `participants[]`; the customer is held during the consult; it resolves to transfer (originator drops), conference (both stay) or consult end (second drops). The receiving agent's Contact Details are the customer's, plus a consult banner (who brought them in, their note) that embeds the same messaging thread with the consulting agent. **Wrap-up is per leg:** `wrapUp` is keyed by participant, so the originating agent gets a wrap-up card for their segment on handoff and the receiving agent gets theirs when the contact ends. The customer's Contact History shows one contact with segments ("Jordan → transferred to Sam"), not two contacts. The agent console window shows an incoming consult as an offer on the customer's contact with the pre-contact summary and the consulting agent's note, not as a bare internal call.
     - **Reporting:** internal time is its own bucket, never handle time. Both cases carry `AgentState`-aware controls: an agent on an internal call is off the queue, which is why contact centers gate the feature by role (agents → supervisors/skills; supervisors → anyone) rather than offer it freely.

## Phase 1 — Vertical profiles and database management

1. **`ContactCenterProfile` type and registry.** Each profile declares terminology (entity name and labels), schema (entity fields + related collections with their status vocabularies), generators, scenario scripts, an intent pack (Tier 1 patterns/slots, Tier 2 tools and system prompt), compliance behaviors, dispositions/reason codes, and a handoff-snapshot template.
2. **Verticals.** Build fully: retail/e-commerce (orders, returns, loyalty, payments), collections (debts, payment plans, promises-to-pay, contact attempts), healthcare (appointments, claims, prescriptions, providers), customer service/tech support (tickets, entitlements, devices, known issues). Thinner packs on the same engine: banking (accounts, transactions, cards, disputes), telecom (lines, plans, devices, outages — the current Marcus Webb data lives here), insurance, travel/hospitality, utilities.
3. **Generator engine.** Shared deterministic synthetic-data engine; per-vertical generators with realistic distributions and status mixes (payments mostly succeeded, some declined, occasional refund; claims with denials; tickets across states), plus showcase records guaranteed to make demo questions land — Marcus Webb gets at least five declined payments.
4. **Named databases on IndexedDB (Dexie).** `SimulatedCustomerDataProvider` takes a database handle; create, switch, export/import as JSON, reset to demo. Entities may carry **several `externalId`s** (Salesforce, Zendesk, CXone contact id, …), since the same person exists in more than one connected system.
   - **4a Interaction history persistence** (added 2026-10-15). On `completeWrapUp` the engine writes the finished interaction (participants, duration, outcome, disposition, tags, summary, transcript, end reason) through `CustomerDataProvider.recordInteraction`, emitting `collectionChanged("interactions")`. Home's Contact History, the customer panel's history accordion (7b) and the Details-panel transcript tab for earlier journey contacts read from it; the page-side "Today" row goes away. Reopen pulls the real prior transcript; unknown callers get a provisional record until linked (P4.9). Export/import JSON includes history. Contract test: a completed wrap-up appears in `getContactHistory(entityId)`.
   - **4b Tickets are native** (added 2026-10-15). `tickets` is a related collection on every profile's schema (id, title, status, priority, owner, the contact that opened it, notes). The app creates, updates and closes tickets itself; "Create ticket" from the wrap-up card carries the summary and disposition in. A ticket links to the interaction that opened it and every later contact that touched it, so history rows show the ticket and the ticket shows its contact timeline. The same records are Phase 7 work items (`kind: "ticket"`). A ticketing connection (Zendesk, ServiceNow, Service Cloud) maps the native schema onto the vendor's under the customer-data sync rules; the vendor's id goes in `externalId`.
5. **Create-database wizard.** Pick vertical → name → size and history depth → seed → optional file import → generate → connect.
6. **Vertical-aware import.** `.csv`/`.xlsx` in-browser (PapaParse / SheetJS), column mapping onto the selected profile's schema, preview, validation, dedupe; extra sheets map onto related collections.
7. **Schema-driven panels** — the real work of this phase. Customer Profile card, Details-panel accordions, and the transactions panel become generic entity + related-collections renderers driven by the profile's schema; the current hard-coded layout survives as the telecom profile's rendering.
8. Route `buildCustomerContextOverviewInfo`, contact history, the dial pad, and the console picker through the provider and profile. Marcus Webb becomes a scenario inside the telecom pack rather than a special case.

## Phase 2 — Realtime chat simulation

**Where threads open: AI display decides where the AI goes; `assignments.legs` decides how legs are presented** (rewritten 2026-10-23; P-AIFIRST (k3) wording kept below for the `tabs` value). **AI display inline and panel: tabs.** Every thread on a card, voice included, is a tab in the record header's toggle group (shown when the card has more than one thread; a lone thread fills the main column with no tab). A tab or the thread's nav row swaps the main column to it (a cross-fade, k5); hover previews stay for inactive tabs (no enter animation), and inactive tabs carry unread counts; the docked panel holds Contact Details only, never a thread. **A call's tab follows AI display like every other thread** (k5, superseding k3's "AI workspace"): inline, its transcript with the AI rows inline and the Copilot composer below; panel, its transcript only, AI in Contact Details. Every tab's session row carries the status pill and Outcome; Session Details opens Contact Details' Session tab on that tab's session. The voice bar is unchanged. An accepted chat always becomes its card's tab; a newly launched or accepted thread, async ones included, is the visible one: its tab, or under "main" the panel's thread (k8 4, which superseded "an auto-accepted async thread never overrides a tab the agent picked"). **AI display "main" (AI-first): the panel.** The main column is the AI workspace, and every thread (a call's transcript, chat, email, SMS, WhatsApp, social DMs) opens in the docked panel, one at a time, with its session row (status pill, Session Details, Outcome) in the panel's header under the channel name; its Session Details swaps the panel to that thread's session details and the thread's icon swaps back — **the one thread that moves** applies here only: an offered thread never rearranges anything, the panel's thread belongs to its card across card switches, and unread counts show on the header icons. **Tempo is static** (voice, chat sync; every text channel async) and still describes channels (the registry, P2.7), but no longer decides the layout. ## Phase 4 — AI assist, Tier 1: deterministic and grounded

1. **`SimulatedAssistProvider`, router half.** Loads the active profile's intent pack: `{ patterns, slotExtractor, collection, query, card }`; runs on every utterance and on agent-initiated asks.
2. **Generic parameterized handlers.** One engine — `getCollection(name, { status?, limit?, sort?, since?, until?, minAmount? })` — with filter/sort executed in code; vocabulary comes from the profile, so "last 5 declined payments" and "last 3 denied claims" are the same code path.
3. **Slot extraction.** Counts, the profile's status vocabulary, recency, date phrases, amounts. "Show me the last 5 declined payments" → `{ status: "declined", limit: 5, sort: "newest" }`. Unfilled slots defer to Tier 2 rather than guess.
4. **Cards render records, not prose.** Cards arrive as `AssistProvider` `card` events (successive full snapshots). Title restates the interpreted query; body is the actual table; a provenance line names the collection.
   - **4a Card-type registry and configurable placement** (added 2026-10-15). Card types (account overview, interstitial, records, text, hint, and new lyra types as they're built) are a registry: a lyra component plus a typed content schema. `AssistCard` gains `type` and `content` shaped by that schema; the provider emits data and the registry picks the renderer, so new lyra types register without page edits. **Lyra rule:** components take a typed `content` object, do no fetching or AI calls, and bubble actions up (`onAction(actionId)`). **Templates per client** (profile config): which fields each type shows, in what order, with what labels, referencing the profile's schema (a retail account overview shows orders and loyalty; healthcare shows coverage and appointments). **Placement:** `pinned` (lives in a Contact Details tab or accordion) or `auto` (appears in the main column's assist slot on a trigger: contact start, intent match, Tier 1 hit, escalation handoff, wrap-up); auto cards can be dismissed. **Interstitials** are auto cards that hold the assist slot until acknowledged (verify identity, compliance reminder), which is how 4.5's gates render. Configured on Settings per profile with preview-as-agent.
5. **Compliance gates in front of cards.** Added to the `AssistCard` contract in this step (deliberately left out of P0.2). Healthcare: nothing PHI-bearing renders until the agent marks identity verified ("Verify identity to view"). Collections: right-party verification and a mini-Miranda reminder card at call start, promise-to-pay capture. Banking: card numbers masked, tying into the existing Mask control.
6. **Placement per channel.** Voice — inline overlay in the main contact container, expands in place. Chat — composer-adjacent suggestion strip, never interleaved into the thread. Expanded state reuses the Details-panel Accordion/card treatment.
7. **Actions map to the app.** "View full history" opens the related-records panel; "Open case/ticket/claim" jumps to it.
8. **Agent ask box** on lyra-ui `ai-input`/`ai-panel`/`ai-process`; same router, same cards.
9. **Progressive entity creation, deterministic half.** Regex extractors for email, phone, ZIP, account/member number, amounts, name heuristics; detected values arrive as `AssistProvider` extracted events and fill the Draft card live, each tagged with its source utterance. Before save, `findNearMatches` offers "Link to <existing>?" vs "Create new." Agent saves with one click or edits; the AI never writes silently. Interaction ended without saving → auto-save flagged *provisional*. On save, the interaction re-associates and Profile/Snapshot/history/table update live; expanded state reuses the existing create form, fields from the profile's schema.
10. No-match fallback: nothing (voice) or a quiet "I can look up <collections>…" hint (chat), listing what the profile actually has.
11. **Knowledge base, Tier 1** (added 2026-10-15; rescoped 2026-10-18 to connect and import, never author — Buyer checklist). Companies already have a knowledge base; the product lets the AI use it. `KnowledgeProvider` gets **connectors** (Zendesk Guide, Salesforce Knowledge, Confluence, SharePoint, a website crawl; read-only, cursor-synced like every import) and **import** (PDF, Word, CSV/Excel, markdown, a URL or sitemap). Both feed one pipeline — extract, chunk, embed, index — with source, URL, last-updated and an access scope on every chunk, so every answer cites what it used and the AI only sees what the signed-in agent could see; the sim indexes by keyword. The router surfaces matches as a `records` card with provenance (title, source, last updated); the agent opens an article in the Details panel or the draggable panel. Admin page AI → Knowledge: sources, sync status, what's indexed, test a question; which sources are active per skill, and whether the AI may quote or only link. No article editor: the quick-reply and template library (11a) is the only authored content.
   - **11a Quick replies** (added 2026-10-16). A native quick-reply library — `{ id, title, body, channels, skills, tags, source: "native" | <vendor>, externalId?, sourceBody? }` — managed in Settings → Knowledge and served by `KnowledgeProvider.listQuickReplies(skill, channel)`. `AssistProvider` ranks and fills them for the current contact; the composer's suggestion chips on chat/SMS/email/WhatsApp draw from the library first and AI-drafted replies second; an AI draft can be "saved as quick reply". **Vendor libraries are sync sources, not replacements:** CXone Quick Replies, Genesys canned responses, Zendesk macros and Salesforce Quick Text map onto the native schema through a connection under the customer-data sync rules — read-only by default (the library is managed in the vendor), two-way when configured — so the agent sees one library whichever system each entry came from.
     - **Variable syntax across vendors.** (1) One canonical form in our data — `{customer.firstName}`, `{agent.name}`, `{case.id}` — against an app-owned variable catalog; vendor syntax never lives in our records. (2) Translation at the adapter edge: each adapter carries a `variableMap` and a tokenizer for its delimiters (CXone `{{FirstName}}`, Zendesk `{{ticket.requester.first_name}}`). On import, an unmapped token becomes `{unknown:<original>}` and the entry is flagged in Settings ("1 variable not recognized"), never silently dropped; on write-back, a canonical variable with no vendor equivalent refuses the write for that entry with the reason; `sourceBody` keeps the vendor's original for a lossless round trip. (3) Render-time safety: every variable resolves against the live contact; one that can't (no first name on an unknown caller) becomes a highlighted placeholder the agent must fill or delete before Send is enabled — for AI-filled replies too.
     - **Formatting:** email replies are HTML; SMS, chat and WhatsApp are plain text. The adapter normalizes per channel on import and the composer strips markup on plain channels.
     - **Vendor-only features** (CXone attachments on a reply, Zendesk macro *actions* such as set-status) don't map to a text reply: the text imports, the rest is recorded as `unsupported` on the entry, and P-MAPPINGS' dry-run preview shows what will and won't sync before anyone syncs.
     - **Templates are the same library** (added 2026-10-16). The quick-reply library generalizes to a templates library: `kind: quickReply | template`; `format: text | html | whatsapp-template`; `channels`; `variables`; `approval: { status: draft | pending | approved | rejected, vendorId? }`. WhatsApp business-initiated messages outside the 24-hour window require an *approved* template (Meta's program, via the CPaaS), so the composer's "Insert template" offers only approved ones there. Sync sources by kind: CXone for quick replies, **Mailchimp** (and the profile's own HTML templates) for email templates, WhatsApp Business via the CPaaS for approved message templates — all through the same `variableMap` / `sourceBody` / `unsupported` machinery. One library, filtered by channel, kind and approval, feeds both the chips and "Insert template".
12. **Agent scripting over FlowProvider** (added 2026-10-18; Buyer checklist → Agent scripting). Scripts are flows with agent-facing nodes, assigned per skill, channel or campaign step; the instruction cards render the current step, utterances advance it, captured fields fill live with the agent's confirmation, and a skipped required step gates Outcome.

## Phase 6 — Virtual agent and escalation to a human

A bot handles the contact first; the customer gets irate or asks for something beyond the bot's authority; the bot escalates, and the human agent takes it over in the app with the whole history in front of them. Both sides of the bot segment are model-driven — no scenario script plays either the customer or the bot (P0.7 scripts remain the console's manual canned-lines panel only). Depends on chat (Phase 2), voice (Phase 3), the handoff snapshot (P2.4), the console (P0.6) and model access (P5.1), so it runs after Phase 5.

1. **Domain and contract.** `Interaction.origin` gains `"escalated"`. `Interaction.escalation?: { at, reason: "customer-requested" | "out-of-authority" | "sentiment" | "bot-uncertain", summary, intent, sentimentTrend, botAttempts[], pendingRequest? }` is written by whoever ran the bot segment and is the only thing the human-side UI consumes. `Message`/`Utterance` get `author: "customer" | "agent" | "bot"` (today's two plus bot); the bot segment is the same Interaction's transcript up to `escalation.at` — same `InteractionId`, same `journeyId`, no second contact. New **`BotAgentProvider`** contract in `src/providers/` (types only): `handle(interactionId)`, `onCustomerTurn(turn)`, `release(interactionId)`; events `botTurn`, `thinking`, `escalate`, `released`; `ProviderError` only; `capabilities` for channels and `canEscalate`. The bot converses and *asks* to escalate; routing stays with the engine (or a real ACD). `ContactCenterProfile` gains a **bot pack**: persona, authority (what the bot may approve, with limits), escalation policy (which triggers apply and their thresholds), and the bot's tools over `getCollection`. Contract tests: `describeInteractionProviderContract` gains "an escalated `incoming` carries `escalation` and `getTranscript` returns the bot segment", gated on a new `InteractionProvider` capability `escalation` so an adapter with no virtual agent skips it per the going-real rule; new `describeBotAgentProviderContract` (turn ordering, escalate fires at most once, `release` cancels in-flight work, `not-supported` gating).
2. **Simulated bot.** `SimulatedBotAgentProvider` in `src/adapters/sim/` on the P5.1 model backends (backend selection lifted into a shared module if it still lives inside the assist adapter). System prompt = the profile's persona, authority and compliance rules; tools = the profile's collection query plus `escalate(reason, summary)`. **Bot-first routing** in `SimEngine`: a console-started contact flagged bot-first is handed to the bot; `escalate` moves it to the queue and the agent app receives `incoming` with `escalation` populated and the bot transcript already in place. The engine honors an explicit "I want a person" even if the model misses it (policy guard, not a script). Chat first.
3. **Console AI-customer mode.** Beside typed and canned lines, "Play as <entity>": a model-driven persona built from the entity record and contact history plus a goal and temperament chosen on the console (refund over the bot's limit, rising frustration, …). It emits ordinary `SimCustomerAction` messages, so the engine can't tell it from a typed customer. During the bot segment the console voices both parties with its own TTS — no agent is on the contact yet.
4. **Agent-side handoff.** Incoming tile shows "Escalated from virtual agent" with the reason; accepting loads the transcript with bot turns rendered distinctly and a handoff divider at `escalation.at` (lyra transcript edit authorized); the handoff snapshot (P2.4) is seeded from `escalation` through the profile's template, then frozen; AI assist resumes over the full transcript. Built once in the shared contact-handling code and consumed by both pages (parity decision). Accept drops the whole bot segment into the transcript at once — a browser check against P2.0's budget.
5. **Voice.** Same path on voice: the bot segment is voiced on the console; on Answer the console stops the bot's voice and `SimulatedMediaProvider` takes over the customer's voice mid-call on the same Interaction, with no re-ring.

## Settings and configuration

Added 2026-10-15. All configuration is data (profile, layout, card templates, KB sources, connections), so it can be edited by hand, shipped as a template, or proposed by the setup assistant.

- **Settings store** (P-SETTINGS, done): a shared store with hooks (`useSetting`, `useSettings`) that the page reads; no page-local setting state. `localStorage`, one key per section, each versioned so a changed setting type falls back to its default; survives reloads and closed tabs; cleared only by "Reset to defaults"; every read/write in try/catch, with defaults when storage is unavailable. Sections: header (apps and their placement, the Home tab order), home (the Dashboard), assignments, outbound, voice, AI, phone, appearance, connections. Profile and database data stay out of it (P1.4).
- **Workspace profiles** (P0.5d.2 renamed the presets; P-PROFILES builds on them). A profile is a named snapshot of every **agent-scope** settings section. Every schema node carries `scope: "agent" | "admin"` (default agent, inherited); admin-scope settings — `appearance.brand`, `channels.social`, and from P-ADMIN every org-level section — are outside profiles by design: `deriveProfile`, `applyProfile` and export/import walk the schema and skip them. ## Administration — the Workspace and the admin areas

Added 2026-10-16. The single page is the **Workspace**, not the Agent Workspace: an agent, a supervisor, a salesperson, an IT tech or a knowledge worker all use it, and what differs between them is a profile and a permission set, never a code path. Everything that configures the org rather than the person lives in admin areas beside the Workspace, reached from the top-left area switcher, and hidden entirely from anyone whose permissions don't include them.

- **Governing principle: simple, AI-led configuration.** Every configuration surface is built so the configuration assistant can do it for the admin, and the hand-built form is the fallback. (1) **Declared before designed** — every setting, list, rule and command exists in the schema or command registry (label, description, defaults, constraints) before it gets a form; the form renders from the declaration and the assistant reads the same one; what can't be declared doesn't get built. (2) **Defaults that work** — every area starts configured from the ContactCenterProfile (dispositions, service levels, agent states, scripts, terminology, recording policy, routing), so setup is adjusting, never filling in. (3) **Conversation first** — "Set up with AI" is the primary entry on every area and on first run: an interview in plain language, a proposed-changes diff, apply on approval; the pages are where you look at what it set. (4) **One page per rail item is the budget** — depth goes into the assistant's interview, not into nested tabs; a surface that needs more than one screen to configure by hand is a signal to improve the assistant. (5) **Plain language both ways** — routing rules, service levels, segments, cadences and scripts can be written as a sentence that the assistant compiles, and every stored rule renders its own sentence back. (6) **Learning** — the org profile accumulates answers so each later area is pre-filled; the first interview is the longest, each later one a confirmation. The "declared before designed" rule is what keeps every admin area assistant-ready; P-CONFIG-ASSIST itself stays in its Phase 5 slot (demo-first), and arrives when there are enough declared areas to make the demo of it convincing.
- **Area switcher.** The top-left label is a switcher over sibling areas: Workspace, Employees, Customers, Channels, Campaigns, Integrations, AI, Branding, Reporting, Billing. The `BrandMark` (logo + name) stays fixed beside it; at that point the default app name becomes "Workspace" (the name is the product, the switcher names the area). For a user with one area it collapses to a plain label (hide, never disable). Areas are data (`buildAppMenuGroups`' list, each with the permission it needs); the switcher is a flat render of it. **The one-page rule is amended:** it governs the Workspace; admin areas are a separate surface that never renders Workspace UI, and the Workspace never imports from them (an ESLint `no-restricted-imports` rule enforces the boundary from P-ADMIN on).
- **Admin shell.** One `AdminShell` (left rail + content) shared by every area; rail items are data per area. The Workspace is the only area without a rail.
- **Settings scope and declared configuration.** Every schema node in `src/settings` carries `scope`, a label and a plain-language description (new fields from P-AIFIRST on; existing fields are back-filled in P-ADMIN); settings forms render from the schema. Admin actions that aren't settings — create group, assign a permission set, run an import, build a dashboard — register as named **commands** with typed parameters. Both exist so that forms, profiles, the audit log and the configuration assistant (below) operate over declarations, never over hand-coded screens. The dividing test for scope: does changing it affect other people, customers or the org? Then admin.
- **Rails** (first pass; refined when each step is planned): Employees — Directory, Groups, Permission sets, Skills, Profiles, Identity (P-EMPLOYEES), Import, Compliance, Audit. Customers — Fields, Mappings (P-MAPPINGS), Data sources, Import. Channels — Enablement, Social (P2.7), Tempo, Templates (P4.11a), Dispositions and Service levels (P-ADMIN), Routing, Agent states and Recording (P-ADMIN-2). Campaigns — Segments, Cadences, Campaigns, Suppression, Consent (P-CAMPAIGNS). Integrations — Adapters, Relay (P-ADAPTER), Connections, Apps & API (P-ADAPTER). AI — Assist, Bots, Approvals, Knowledge. Branding — Identity (name, logo), Colors, Terminology. Reporting — Dashboards, Reports, Exports. Billing — Usage, Rate card, Budgets, Invoices. Channel enablement (`channels.*`) stays agent-scope until P-EMPLOYEES moves channel entitlement onto permission sets; then it moves to admin and leaves the Phase 1 / Phase 2 profiles.
- **Employees** (P-EMPLOYEES, after P0.9; a view onto `DirectoryProvider`). "Agent" is a role within it, beside supervisor, sales, IT, knowledge worker. **Permission sets** are named bundles: which areas are visible, which actions are allowed (approve, export, edit knowledge, manage templates, assign profiles, use AI features, view usage, …), which channels the person can take; built-ins Agent, Supervisor, Admin, Read-only. **Groups** are teams or any set of employees; a group carries a permission set and a default workspace profile. Permission sets attach to groups; an individual can get an extra set or an explicit deny; effective permissions = union of group sets + individual grants − individual denies, and every employee page shows the effective result with where each permission came from. **Role is an attribute** (job title) that seeds a new or imported employee's defaults — group, permission set, workspace profile — and has no behavior of its own. Hide-never-disable gates on effective permissions everywhere: the switcher, Workspace actions, channels offered. **Session resolution:** a `SessionProvider` seam (`currentUser`, effective permissions, resolved workspace profile, default area) that everything downstream reads instead of `DirectoryProvider` directly; the existing login screen becomes a simulated sign-in ("Sign in as…" over the directory's personas, plus a form that accepts anything); landing is the Workspace with the profile applied before first paint, or the first permitted admin area for a user with no Workspace permissions; area in the URL for deep links, unauthenticated hits redirect to login and back; sign out in the app menu. **Acceptable Use** is a login step: versioned terms (edited under Employees → Compliance), acceptance recorded per user with version and timestamp, re-acceptance forced when the version changes, a report of who accepted which version; the terms prohibit automating or modifying the app with extensions, scripts or agents. **Audit log:** every admin action and every configuration-assistant proposal recorded with actor, command, before/after and approval state; exportable. Group/individual assignment UI for permission sets and workspace profiles is the same screen and lands with Phase 7 My Team.
- **Import, with history** (P-IMPORT, after P-MAPPINGS and P-ADAPTER). Switching platforms is the real barrier, so import is a shared engine surfaced as Employees → Import and Customers → Import. Adapters gain `exportEmployees()` / `exportHistory()` jobs beside the relay's (CXone, Genesys, Five9, Zendesk, Salesforce; CSV/Excel as the escape hatch), simulated with fixtures. Four steps: pick source → map fields (the P-MAPPINGS mapper, auto-suggested) → preview with dedupe (match on email / external id, merges vs creates) → run, with a results summary. `Employee.externalIds: { [source]: id }` so a re-import updates instead of duplicating; imported skills, roles and teams map onto Groups/Skills, unmapped values land in a "needs review" bucket; **historical interactions and metrics load into `ReportingProvider` with a `source` dimension and their original timestamps**, so a dashboard shows the pre-migration baseline on day one; role defaults apply on import so a migrated agent lands in a working permission set and profile.
- **Reporting and supervision** (P-REPORTING, after P-EMPLOYEES; moved up 2026-10-18 because the supervisor's live view is the same surface). `ReportingSink` stays the egress seam; a new **`ReportingProvider`** is the in-app read model, deriving metrics (volume, handle, hold, after-call, CSAT, queue, per agent, per channel, per group, internal time as its own bucket) from the simulated interaction history and `recordInteraction`. **Dashboards:** a widget grid (KPI tile, time series, breakdown, table); add, remove, resize, reorder; several named dashboards, one default; layouts are content, stored in the provider, not in `src/settings`, though a profile may name a default dashboard. **Reports:** pick a type, set filters (date range, agent, group, channel, queue), run, get a sortable table and a chart; saved definitions. **Exports:** CSV and PDF of any report or dashboard, downloaded as a real file; an export history. Playwright for the grid. Later: an agent-facing "My stats" view in the Workspace on the same provider. **Two time horizons, one surface.** `ReportingProvider` serves historical aggregates (from `recordInteraction`) and a **live model** derived from the interaction store and `DirectoryProvider`: agents by state with duration, queues with waiting count and longest wait, SLA against target, active interactions by channel. A widget declares `live` or `range`; both sit on the same grid. **Supervisor actions are widget actions**, permission-gated (hide-never-disable) and logged: an agent tile offers monitor / whisper / barge (voice, through the MediaProvider seam, simulated), change state, force logout, message; a queue tile offers reassign skill and change priority; a live-interaction row opens the interaction read-only. **Wallboard mode** is a flag on a dashboard: full-screen, auto-rotating pages, large type, no actions. **Thresholds and alerts** on live tiles (SLA breach, queue over N, agent in a state over M minutes) set tile state and notify the supervisor — the existing hold-time SLA banner is this pattern. A supervisor's profile lands on their default dashboard; an agent's "My stats" is the same provider scoped to self. Dave's real-time dashboard designs are the spec for the first dashboards; P-REPORTING's plan maps each tile to a provider query and its actions. **One supervisor experience, three sources:** live operations (this step), quality (P-QM) and workforce (the WFM adapter) all surface on the same dashboards as tiles and WorkItems — a Needs-review queue of AI-flagged interactions, team quality scores and coaching assignments from P-QM; adherence (scheduled vs actual state from the Phase 7 schedule), staffing vs forecast, and shift-swap / time-off approvals from WFM. QM keeps one dedicated screen (evaluation form with synced playback); WFM gets none — forecasting and scheduling stay in the vendor's product behind the adapter. No separate supervisor, QM or WFM consoles.
- **LLM access and metering** (P-BILLING, after P-REPORTING and P5.1). **`LLMProvider`:** `AssistProvider`, `BotAgentProvider` and the configuration assistant all call the model through one seam, simulated or real; one place to swap, one place to meter. **`UsageProvider`:** every call records model, input and output tokens, cost at a configured rate card, timestamp, user, group, feature (copilot, autosummary, bot, config assist, reporting) and interaction id; nothing reaches a model except through this path, so nothing goes unmetered. **Billing area:** Usage (by feature, group, employee, model, over time), Rate card, Budgets (monthly caps per group; soft warning, then a hard stop that hides AI features, never disables them), Invoices (simulated statements, exportable). Reporting gets a usage widget. "Use AI features" and "view usage" are permission-set entries, so an org can run no-AI seats.
- **Configuration by conversation** (P-CONFIG-ASSIST, with Phase 5 §7, which it generalizes). A simulated **`ConfigAssistProvider`** on `LLMProvider`. "Set up with AI" on every admin area and on first run: it interviews (how many teams, which channels today, who approves refunds, which systems), maps answers onto settings and commands, and shows a **proposed changes** diff in the existing cards/approvals pattern; nothing applies without approval, it only proposes within the admin's permissions, and it emits only the typed schema and registered commands. Answers accumulate in an **org profile** (industry, size, channels, terminology, systems) that pre-fills later interviews and adjusts defaults — by Reporting it already proposes the dashboards that fit; the org profile is visible and editable, stored in the provider. The same assistant works an agent's own settings from the Workspace ("make my layout AI-first") with the same approval card. Phase 5 §7's templates half and Phase 7 §8's auto-tune are sources of proposals into this one flow.
- **In-app only.** AI configures and operates the app only from inside it: no API or registry exposed on `window`, no external agent access, `data-*` test hooks stripped from production builds. Browser extensions can't be prevented by a web app, so the posture is deter, detect, bind: strict CSP; an integrity monitor (unexpected DOM mutations on key controls, injected scripts, inputs with no preceding pointer or keyboard activity, inhuman cadence) that logs "possible automation" to the audit log and a Compliance report, optionally forcing re-acceptance or locking the session per an admin setting (simulated, with a toggle to fire a sample detection); Acceptable Use as the binding term; and an admin page pointing customers at Chrome/Edge enterprise policy, which can block extensions at the browser level and is theirs to enforce.
- **Small-screen and embedded Workspace** (P-EMBED, the last step). A second app shell, not a second codebase: `apps/full` (switcher, admin areas, Workspace) and `apps/embed` (Workspace only, framed into Salesforce or Zendesk or opened on a phone), both over shared `packages/workspace`, `packages/providers`, `packages/settings` and lyra. The restructure is mechanical if three boundaries have held from now: (1) the Workspace never imports from admin (the ESLint rule above); (2) a **`HostProvider`** seam gives the Workspace its session, current customer/case and "where am I running" — standalone = today; embedded = iframe with `postMessage` (the host passes the open record and an SSO token in, the Workspace sends status and wrap-up out; Salesforce Canvas and the Zendesk Apps framework fit it); (3) layout responds to **container width, not viewport**, via container queries, with a stacked small-screen mode where the docked panel becomes a full-width sheet and placement collapses to one visible region at a time — a layout setting with an `auto` value, the same mechanism as conversation placement, so a 400 px Zendesk sidebar and a phone are one mode. The embed has no switcher and no admin, personal settings reduced to what fits, white-labeling from the org, Acceptable Use passed through from the host session; metering is unchanged. P-EMBED: the two shells, the embedded `HostProvider`, the container-query pass, Playwright at 400 px and phone widths, and a mock host page that frames the embed and exchanges messages.
- **Deferred question, not a decision:** Sales and IT personas will want work items that aren't conversations (opportunities, tickets as the primary thing). Phase 7's `WorkItem` is the likely home; whether `Interaction` generalizes is decided there, never in P-AIFIRST, P-PROFILES or P-ADMIN.

## Internationalization — the Workspace in any language and direction

Added 2026-10-18. Customers will run the Workspace in Arabic, Hebrew, Cyrillic and CJK languages as well as English. Direction, script and locale are therefore first-class, and the cost of getting there is lowest while the string surface is small, so the convention starts now and the implementation lands before Phase 4 adds the bulk of the AI card text.

- **Two problems, kept apart.** *UI language* is what the agent and admin see: every label, date, number and layout direction. *Customer language* is what the customer writes or speaks and the agent may not read: detect, translate inline, reply in kind, keep a bilingual transcript. The first is this section (P-LYRA-RTL, P-I18N). The second is an AI assist feature in Phase 4/5 and touches the Message model (original and translation stored side by side, with which is which); it is planned there, not here.
- **Convention from now (CLAUDE.md rule).** No user-visible string literal in a component: strings go through `t()` from the app's i18n layer with English as the source locale; ICU message format for plurals and gender. Dates, times, numbers and currencies through `Intl.*` with the active locale, never hand-formatted. Layout in logical properties (`ms-`/`ps-`/`start-`/`text-start`, not `ml-`/`pl-`/`left-`/`text-left`). Scenario content (Lucas, Marcus, Tom, Maya scripts) is content and is translated as data when P1.8 moves it there, not wrapped in `t()`. Code written before this rule is swept in P-I18N.
- **P-LYRA-RTL** (lyra-ui, authorized as its own lyra pass; before P-I18N). (1) Every physical Tailwind utility in lyra becomes its logical equivalent; `dir` on the root is respected by every component; icons that mean direction mirror in RTL (back, forward, chevrons, send, indent), icons that don't (clock, phone, logo, play) never do. (2) Script-aware type tokens: font stacks with fallbacks that cover Arabic, Hebrew, Cyrillic and CJK; line-height and vertical rhythm that hold for taller Arabic and CJK glyphs; `word-break`/truncation rules for CJK (no word spaces). (3) Storybook stories under `dir="rtl"` and with CJK/Arabic sample text for the components the Workspace uses; lyra's Playwright or visual check covers them. `.lyra-ui-sync` bumped; the app's own sweep follows.
- **P-I18N** (the app; after P-LYRA-RTL, after P-ADMIN). The i18n layer (`i18next` + ICU; `src/i18n/`), an extraction script that generates the English locale file from `t()` keys and fails CI on an unwrapped literal, and the one-time sweep of code written before the rule. `locale` is an admin-scope setting (org default) with an agent-scope override; `dir` derives from the locale. Identifiers that are always LTR inside RTL text (phone numbers, order and case ids, emails, URLs, `CTX-…`) render in a `Bidi` span with `unicode-bidi: isolate`. Pseudo-localization (long accented strings, RTL mirror) as a dev locale so truncation and mirroring show without a translator. Playwright: the three AI display modes and the Settings page under `dir="rtl"` with pseudo-locale, and one CJK pass for truncation. Translations are content: locale files live beside the scenario content and the configuration assistant may later propose them; none ship in P-I18N beyond English and the pseudo-locale.
- **Terminology: standard nouns, renamable by the customer.** One canonical term set with stable keys (`terms.customer`, `terms.contact`, `terms.agent`, `terms.skill`, `terms.team`, `terms.segment`, `terms.campaign`, `terms.cadence`, `terms.disposition`, `terms.case`, …), each with singular and plural, rendered everywhere through `t()` and never hardcoded. Defaults are general contact-center nomenclature so a CXone, Genesys or Five9 admin recognizes them on day one (Customer, Contact, Agent, Skill, Team, Segment, Campaign, Cadence, Disposition, Case). The active ContactCenterProfile supplies vertical defaults (healthcare: Patient; collections: Account; hospitality: Guest) through its `terminology` map (Phase 1), and the org can override any term in **Branding → Terminology**, which writes a locale overlay (admin-scope) that `t()` resolves above the profile's defaults; plurals and gender follow ICU. Code-level type names (`Interaction`, `Entity`, `WorkItem`) are not display terms and never change. The configuration assistant may propose overrides from the org profile ("you said members").
- **Touches elsewhere.** Phase 1's generators produce locale-appropriate names, addresses and phone formats per vertical profile. P4.11a templates and quick replies carry a `language` and the library filters by the thread's language. Acceptable Use text (P-EMPLOYEES) is per locale and versioned per locale. Reporting's exports format per the viewer's locale. The embed (P-EMBED) takes locale and `dir` from the host session.

## Compliance — PCI DSS and SOC 2 as architecture, not paperwork

Added 2026-10-18. Many customers won't evaluate a contact-center product that isn't SOC 2 attested and PCI DSS compliant. SOC 2 certifies the organization's controls over time and PCI governs cardholder data; neither is something code "is", but the code decides whether either is achievable. The seams already in the plan (audit log, permission sets, SessionProvider, the relay as the only credential holder, in-app-only AI) are most of the architecture; this section adds what's missing and names the step.

- **Cardholder data never enters the app** (the PCI posture every contact-center vendor uses). A **`RedactionProvider`** seam sits in front of every message, utterance and transcript write and every read by `LLMProvider` or `ReportingSink`: PAN (Luhn-checked), CVV, expiry, bank account, SSN; per-vertical additions from the ContactCenterProfile (healthcare adds PHI fields in Phase 1). Matches are replaced by a token and a display form (`•••• 4417`) before storage; the model only ever sees redacted text. Voice: the bar's **Mask** becomes a real state — the simulated recording and transcript pause, the session row shows the gap, the audit log records it; a real deployment hands masked audio to a DTMF/tokenization service in the relay. Chat, SMS, email and WhatsApp redact automatically on ingress and on send. PCI scope then shrinks to the relay and the tokenization vendor.
- **Call and screen recording** (seam and policy in P-COMPLIANCE; playback in P-QM). A **`RecordingProvider`** seam behind the voice bar, the Compliance rules and QM: `Recording { interactionId, agentId, kind: "voice" | "screen", startedAt, endedAt, segments (recorded / paused / redacted — the Mask gaps are explicit redacted segments, never silence), consent, retentionClass, storage locator }`. Screen capture can't come from a web app, so `screen` is a capability the sim fakes and a real deployment supplies from the desktop app or the embed host; without it, screen controls are hidden. **Policy, not buttons** (Channels → Recording in P-ADMIN-2): auto-record per skill and channel (all / sampled N% / none), who may pause and the Mask rule that forces pauses, a consent prompt per jurisdiction (two-party states, GDPR) recorded on the Interaction, retention class per kind, who may play back. The voice bar's Record is a manual override within policy — an agent can't stop a mandated recording and the button shows the reason (`DisabledReason`). **Playback** (P-QM): recording synced to the transcript, scrub by utterance, screen beside audio, redacted segments shown as gaps, every playback a logged access; Contact Details → Session links to it. Retention, erasure and encryption follow the Data handling bullet.
- **Audit log hardening** (the SOC 2 evidence trail). Append-only with a hash chain; every event the trust criteria name: authentication, permission and group changes, data access and exports, config changes, AI proposals and approvals, redaction and mask events, retention actions. Retention is a setting; export for auditors is a logged, permissioned action.
- **Access controls** that the Employees step leaves open: session timeout and re-authentication, MFA at the simulated login, least-privilege defaults on the built-in permission sets, data export as its own permission, break-glass access that is time-boxed and logged.
- **Data handling.** Retention and deletion per record type (transcripts, recordings, PII, audit); right-to-erasure for a customer as a command; encryption at rest and in transit as a relay/storage responsibility named in Connections; no PII in browser storage beyond the session — the contact-methods overlay and anything in `localStorage` are reviewed here and move behind a provider or are cleared on sign-out.
- **Admin surface.** Employees → Compliance grows from Acceptable Use into the compliance home: redaction rules and test, retention, audit search and export, mask policy, and a **controls checklist** mapped to SOC 2 trust criteria and PCI DSS requirements, each with its evidence link into the audit log — a strong demo moment and the artifact an auditor asks for.
- **P-COMPLIANCE** lands after P-EMPLOYEES (it needs the audit log and permission sets) and before P-REPORTING (reports and exports must redact). Nothing before it changes except the convention below.
- **Convention from now (CLAUDE.md rule).** No code path passes raw message, utterance or transcript text to `LLMProvider`, `AssistProvider`, `BotAgentProvider` or `ReportingSink` except through the redaction seam; until P-COMPLIANCE lands it, the seam is an identity pass-through in `src/providers/redaction.ts`, so Phase 2 and Phase 4 are written against it.

## Outbound campaigns — segments, cadences and the dialer

Added 2026-10-18. Customers run outbound as programs, not one call at a time: define who (a segment), define the sequence of touches (a cadence), run it (a campaign), and have replies land back in the Workspace with context. This is a new product surface with its own admin area and seam. It is late in the order because it depends on templates, permissions, redaction, locale and WorkItem; the one decision that must hold from now is the record shape.

- **Record shape (decided now).** A sent cadence step is an ordinary `Interaction` with `origin: "campaign"`, `campaignId`, `cadenceStepId` and `enrollmentId` — never a second record type. It appears in Contact History, Contact Details and reporting like any other, and a customer's reply re-enters inbound routing with the campaign attached as context the agent and the AI can see.
- **Segment.** A saved query over customers: rules on profile fields, tags, interaction history and per-channel consent, with a live count and a preview list. Dynamic (membership re-evaluated at each run) or a static snapshot. The rule builder is schema-driven from the ContactCenterProfile (Phase 1), so vertical fields appear without code; the configuration assistant can propose a segment from a sentence.
- **Cadence.** An ordered set of steps, each `channel + template (P4.11a) + delay + condition`, with branches on reply / no reply and exits on reply, conversion event, opt-out, do-not-contact or max attempts. Rules per cadence: contact windows in the customer's local time (the locale and time-zone work in Internationalization), caps per channel per day, channel fallback. Voice steps are **dialer** work — preview, progressive, predictive — delivered to agents as offers carrying campaign context; a queued callback is a Phase 7 `WorkItem`.
- **Campaign.** A cadence running against a segment: start, pause, stop, throttle, agent/skill assignment for voice steps, and metrics (enrolled, reached, replied, converted, opted out, cost). Each enrollment holds its position in the cadence.
- **Compliance is load-bearing** (hence after P-COMPLIANCE): consent per channel recorded with source and time; calling-hour windows and frequency caps enforced by the scheduler, not the UI; suppression and do-not-contact lists honored before every step; every send, skip and exit in the audit log; message copy passes through `redact()`; template approval status respected for WhatsApp.
- **Seam and sim.** A **`CampaignProvider`** owns segments, cadences, campaigns and enrollments and a scheduler that fires steps through the InteractionProvider's existing dial/send path, so latency, auto-accept and presence rules apply unchanged. The sim scheduler runs on the page clock so a demo can advance a week in seconds and show replies arriving. Real adapters map to the vendor's campaign/dialer APIs in P-ADAPTER's order.
- **Admin area: Campaigns** — Segments, Cadences, Campaigns, Suppression, Consent. Reporting gains campaign metrics and a funnel widget; Billing meters AI-drafted message copy.
- **P-CAMPAIGNS** lands after P-COMPLIANCE and Phase 7; campaign metrics and the funnel widget are added to P-REPORTING's dashboards when P-CAMPAIGNS lands. Nothing before it is blocked; Phase 7's WorkItem design should allow a "callback" kind with campaign fields.

Sign-in **methods are a registry**: `local` (the demo's "Sign in as…"), `oidc` and `saml` generic, and named presets that are OIDC configs with a logo — Salesforce, Microsoft Entra, Google, Okta, Zendesk. The routing engine, the live dashboard tiles (P-REPORTING) and the alert rules read them; today's hardcoded hold-time SLA banner becomes the first consumer.

## Flows — IVR, studio workflows and the contract that lets them wait

Added 2026-10-18. A visual flow builder (CXone Studio, Genesys Architect, Amazon Connect flows) is a product of its own and lands last. What lands early is the **contract**, so everything built in between produces or consumes flows and the builder plugs in without rework.

- **Flow definition.** A JSON document the engine executes: `nodes` (play prompt, collect input, menu, condition, lookup via CustomerDataProvider, set variable, queue to skill, transfer, bot (Phase 6), offer callback (the P0.9 WorkItem), send message/template, survey, hang up / end), `edges`, `variables`, and a `trigger` (inbound on a channel or number, a routing rule, a cadence step, a schedule). Versioned; a published version is immutable.
- **Node registry.** Each node type registers an executor and, later, its canvas card and property form, so vendor-specific or customer-specific nodes are additive. The registry is the plug-in point.
- **`FlowProvider` seam** (P0.9, alongside the callback WorkItem): list, get, publish, run; the sim implementation is an interpreter that walks the JSON on the page clock. `routeInbound` accepts a flow as a target beside a skill. The scenario scripts (Lucas, Marcus, Tom, Maya) are the first flows: P1.8 converts them to the flow shape when it moves them to data, which proves the contract before the canvas exists.
- **Consumers already in the plan:** routing rules (P-ADMIN-2) may target a flow; Phase 6's bot is a node; a survey is a flow; a P-CAMPAIGNS cadence is a flow with delay nodes; the configuration assistant may propose a flow from a sentence.
- **Flows admin area (P-ADMIN-2, minimal):** list, import/export JSON, set trigger, choose version, run in the sim — no canvas.
- **IVR** is a flow whose trigger is a voice number and whose nodes are prompts and collections; **visual IVR** is the same flow rendered as a web page by the embed shell. Neither is a separate product.
- **P-STUDIO** (after P-CAMPAIGNS, before P-EMBED): the visual canvas on lyra (nodes, wires, property panels), test-run against the sim with a live trace, versioning and publish with diff, and **importers for CXone Studio and Genesys Architect exports** so customers bring their flows — the same switching-cost story as P-IMPORT. Its own admin area replaces the minimal one.

## Customer data: the app is the source of truth

Added 2026-10-15. The app's database is the system of record for the agent's work; CRMs, ticketing systems and KBs are feeds and sinks.

- **The AI reads only `CustomerDataProvider`**, never a CRM adapter, so it always sees the latest notes, Draft saves, outcomes and history (1.4a), even when sync is behind or the connection is down.
- **Sync modes per connection:** `manual` (file import, 1.6), `interval` (poll every N minutes), `realtime` (webhooks or a vendor event stream through the relay). A CRM adapter per source (Salesforce, Zendesk, HubSpot, Dynamics) maps vendor records onto the profile's schema with the same column mapping as 1.6, saved as a reusable mapping; related collections (orders, tickets, cases) map the same way. `entityChanged`/`collectionChanged` refresh Profile and Snapshot live mid-contact. The sim gets a "simulate sync" control that mutates records on an interval, and a "simulate conflict" control.
- **Write-back:** local edits queue through the adapter when the connection allows; a record with pending writes shows a "pending sync" chip. Writes are idempotent (client-generated change id) and retried; a rejected write (vendor validation) stays queued with its error shown on the record.
- **Conflict handling:** per-field `authority: app | crm | newest` in the profile schema (contact facts default to `newest`; notes and dispositions to `app`), with the losing value kept in a conflict note on the record. Timestamps are the vendor's `lastModified` and the proxy's clock, never the browser's. Never delete locally on sync: a record deleted or merged in the CRM is marked "archived in CRM" and keeps working; merges map through `externalId`. Unknown vendor fields are kept raw under the record and listed as unmapped in the mapping screen; sync never fails outright. A "Sync" section on Settings lists conflicts, pending and failed writes with resolve/retry.
- **Provenance per field:** where it last came from (agent, CRM import, AI extraction) and when, shown on cards ("updated by you 2 min ago" / "from Salesforce 1h ago"); P4's provenance line reuses it.
- **Offline:** the app works with every connection down; sync catches up later.
- Contract tests: an agent edit is visible to `suggest()` before any sync; an import doesn't overwrite a newer local edit; write-back queues and drains; same-field conflict by authority; delete-while-open; rejected write retry; unknown field preserved.

## Integration readiness — how we know the seams will hold

Added 2026-10-15. The pages never test against a vendor; they test against the contract, and the contract is what every vendor adapter has to satisfy.

- **One contract suite per seam, and a real adapter is done only when it passes it:** `InteractionProvider` (P0.8), `CustomerDataProvider` (P1.4), `BotAgentProvider` (P6.1), `DirectoryProvider` and `MessagingProvider` (P0.9), `KnowledgeProvider` (P4.11), `WorkProvider`, `AppProvider`, `ReportingSink` (Phase 7). An adapter may skip a test only where its own `capabilities` say the feature is off.
- **Contracts are shaped from the vendors, not from the sim.** Before each seam's contract is final, a mapping checklist against the real APIs (CXone Agent API events, Twilio TaskRouter/Conversations, Genesys Platform API, Zendesk tickets, Mailchimp campaigns, a WFM schedule export, Salesforce/Zendesk records) records how each method and event maps and what doesn't; what doesn't map becomes a capability flag.
- **Vendor shape is data: outcome scope, timing, presets (added 2026-10-23).** Every platform is translated into the Assignment model by its adapter; nothing in the UI branches on a vendor name. The adapter declares capabilities and a **connection preset** seeds the settings that shape the UI: `capabilities.outcomeScope: "assignment" | "leg" | "both"` — `assignment` = one Outcome, legs inherit (Zendesk, Generic); `both` = one Outcome that fans out to each leg with a collapsed "applies to all N channels · change" row for per-leg overrides (CXone, Genesys, Salesforce); `leg` = one Outcome per channel (dialer-style platforms; today's behaviour); `capabilities.outcome.dueAt: "assignmentEnd" | "legEnd"` — on `legEnd` vendors (CXone, Five9, Talkdesk) a leg that closes while others stay open shows an inline "Disposition this call" prompt on its lifecycle row, prefilled from the assignment's running Outcome draft and the AI summary, written by the adapter at ACW; the final Outcome still fans out and updates what the vendor allows; `capabilities.assignment.split / merge / transfer` — shown only when declared (hide, never disable). Terminology presets set `terms.*` (CXone → Contact, Genesys → Conversation, Salesforce → Case/Work Item, Amazon Connect → Contact, Twilio Flex → Task, Zendesk → Ticket, Generic → Assignment); dispositions and not-ready reasons import from the vendor's lists (P-ADMIN/-2). A platform with no grouping concept gets one synthesised assignment per leg, merged by customer when the agent adds a channel; one with a grouping we lack maps it to the assignment and the rest to legs, overflow on `externalId`/attributes. **The contract suite** gains an outcome section parameterised by the declared scopes; an adapter is done only when it passes it. `ReportingSink` emits leg events always plus one assignment outcome event. Unknown platforms start from the Generic preset and fill the same mapping table (docs/assignment-terminology-map.pdf, page 2) through Connector Mappings; the setup assistant can draft it from the vendor's API docs.
- **One small backend:** a proxy/relay service holding vendor keys, exchanging tokens, and receiving webhooks as a websocket relay (the reason `SimTransport` swaps for a websocket). P5.1's model proxy is the same service. The browser never holds a secret.
- **The relay is a real deliverable, not glue** (added 2026-10-16). Vendors push events by webhook — an HTTP POST to a URL we own when a call arrives, an SMS lands, a call ends, a recording is ready — and a browser tab can't receive one, so the relay is the only place a real integration can start. It owns four jobs, each vendor-agnostic in the same way the adapters are:
  - **Webhook receiver:** public URLs per connection, signature verification (Twilio `X-Twilio-Signature`, Zendesk/Salesforce HMACs), idempotency on the vendor's event id, and a dead-letter log for anything it can't parse.
  - **Routing decisions for voice:** for Twilio the webhook *response* is the instruction (TwiML: connect to this agent's browser client, hold, queue, transfer), so the engine's routing rules (skill, presence, channels, one call per customer, auto-hold) run in the relay for real, not in the browser. CXone keeps routing on its side; the relay only forwards.
  - **Fan-out to agent sessions** over the WebSocket `SimTransport` becomes; each vendor payload is translated by the adapter into our domain events (`incoming`, `message`, `stateChanged`, `ended`, `collectionChanged`) before it reaches a browser. Nothing in the UI changes.
  - **Outbound webhooks:** Data Memorialization (P-MAPPINGS) is the relay writing to the connected system or firing a configured URL on a trigger; inbound CRM webhooks (a ticket updated elsewhere) become `collectionChanged` under the customer-data sync rules.
  - Built in P-ADAPTER's first step (Twilio) and reused by every later adapter; record-and-replay captures its webhook payloads as fixtures so the suites run without a vendor.
- **Carriers are not a seam** (added 2026-10-16). One CPaaS account (Twilio, Vonage, Telnyx, Bandwidth) carries voice and SMS on the same numbers, so a customer connects one platform and both channels work; carrier choice, BYOC/SIP trunks and number inventory live inside the adapter. A second connection appears only when the customer connects a second *platform* (CXone for voice, a CPaaS for SMS/WhatsApp), never to model a second carrier. Channel onboarding is per channel regardless of carrier (US SMS: 10DLC or toll-free verification; WhatsApp: Meta's business program). Settings → Connections shows "Phone system: Twilio (voice + SMS)" as one row with its numbers under it.
- **Per-channel capabilities** (added 2026-10-16). Rich messaging differs by channel and by number, so the provider's `capabilities` map gains a per-channel block the composer reads: `channels.sms.media` (MMS), `channels.whatsapp.interactive`, `channels.whatsapp.templates`, `channels.rcs.richCards`, `channels.email.html`, `channels.*.attachments`. The CPaaS reports these per number; the adapter fills them; the sim sets them all on. Hide, don't disable: a composer control for a capability that's off doesn't render.
- **Identity:** several `externalId`s per entity, so one customer maps across systems.
- **Record and replay:** when a real adapter runs, capture vendor events as JSON fixtures and replay them in tests, so the suites cover real payloads and the real integration can be demoed offline.
- **Connector mappings and data memorialization** (P-MAPPINGS, before P-ADAPTER; Zendesk needs it). Each Connection in Settings gets two sub-tabs:
  - **Connector Mappings:** for each of our entities (customer, ticket, account, interaction, quick reply — P4.11a), a field-by-field map to the connected system's object and fields, with a direction (lookup / write / both) and a per-field authority (app wins / system wins / newest wins; the authority model from "Customer data" above), plus the search keys used for identification and screen pop.
  - **Data Memorialization:** named mappings (name, description, entity type, field set) that run on a trigger (contact accepted, outcome saved, wrap-up complete, transfer) and write interaction data (disposition, notes, duration, transcript link, agent, skill) to the connected system. Several per connection, with a dry-run preview.
  - Stored in the settings store under `connections.<seam>.mappings`; the sim adapter logs what it would have written.
- **Prove the pattern early, in order:** Twilio (free trial, well documented, real calls) → Zendesk (free sandbox, plain REST, tickets) → CXone (the one that matters; needs a tenant and Agent API credentials) → a WFM adapter → an AI-agent vendor. Each is a P-ADAPTER step with its own suite run.
- **Data warehouses and change streams** (added 2026-10-18; a P-IMPORT and P-ADAPTER concern, no code now). Customers' interaction history usually already lives in a warehouse (Snowflake, Databricks, BigQuery, Redshift) fed by CDC tooling (Fivetran, Debezium over Kafka, native streams). P-IMPORT's engine is therefore **cursor-first**: every source adapter exposes `changesSince(cursor)` and the import loop consumes deltas and advances the cursor, with a full load being the degenerate first call — never "fetch everything" as the primary path. The simulated adapters emit the shape of a real change feed (an action column, an offset) so a real one is a transport swap behind the same engine. Real warehouse and Kafka connections run only in the relay (credentials and protocols a browser can't hold); they are adapters in P-ADAPTER's readiness order after the vendor ones, and warehouse polling respects compute cost (streams/tasks or scheduled pulls, not tight polling). This is recorded so P-IMPORT and P-ADAPTER are planned around it; nothing before them changes.
